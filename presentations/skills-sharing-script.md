# Skills 团队分享——完整讲稿

> 预计时长：40–50 分钟（含互动）
> 目标听众：团队全员（研发 + 产品 + 设计 + 管理者）

---

## 第一部分：为什么要聊 Skills

**【幻灯片 1：封面】**

大家好，今天想和大家聊一个话题——Skills。

先说个现象：我们团队现在用 AI 工具已经越来越多了，不管是写代码、写文档还是做分析，大家或多或少都在用。但是用了一段时间之后，有没有发现一些新的问题开始出现？

**【幻灯片 2：这些场景你遇到过吗？】**

我列几个场景，大家看看有没有共鸣：

- **同一种 bug 修复流程要反复说一遍。** 每次让 AI 修 bug，你都要重新告诉它"先理解问题、再搜索代码、再写修复、再补测试、最后总结根因"。说一次还行，说十次就烦了。
- **同一种 review 格式每次都要重新要求。** 你希望 AI 审代码时关注安全性、性能和可读性，但每次开新会话都要重新说一遍。
- **高质量的做法只存在于少数人的聊天记录里。** 你团队里可能有一个人特别擅长让 AI 写出高质量代码，但他的方法别人根本不知道，也没法直接复用。
- **每个人都在手写一套相似但不一致的操作流程。** 三个人让 AI 做同一件事，输出格式完全不同，质量参差不齐。

这些问题的本质是什么？我们已经"会用 AI"了，但我们还没有把"会用"变成"可重复、可共享、可维护"。

今天这个分享就是要解决这件事——怎么用 Skills 把团队使用 AI 的最佳实践固化下来。

---

## 第二部分：Skills 是什么

**【幻灯片 3：什么是 Skill】**

### Skill 的定义

先从最核心的概念讲起。

**Skill，简单说就是一个"带说明的主动工作流入口"。**

什么意思呢？当你有一个复杂的流程需要 AI 帮你做，比如修 bug、生成测试、做 code review、写日报，你不想每次都从头描述一遍这个流程应该怎么走。你把这个流程写成一个 Skill 文件，下次只需要一个命令就能调起来。

在 Claude 里，你输入 `/fix-bug`，在 Codex 里输入 `$fix-bug`，AI 就知道按你预设的流程来工作——先理解问题、搜索代码、做最小修复、补测试、格式化输出。

**核心词是三个：主动发起、固定流程、可复用。**

**【幻灯片 4：什么是 Hook】**

### Hook 的定义

讲 Skill 的时候必须提一下 Hook，因为它们是一对搭档。

**Hook 更像是"在某个事件发生时自动执行的一段守门逻辑"。**

举几个例子：

- 每次开新会话，自动加载当前项目的环境信息——用的是什么框架、什么包管理器、什么测试工具。这个就不需要你每次手动说，配一个 Hook 就好了。
- 有人在 main 分支上直接让 AI 改文件？配一个 Hook，在文件写入前自动检查分支，如果是 main 就直接拦截。
- AI 调了一个 Shell 工具？配一个 Hook，自动记录这次调用的命令和输出。

核心词也是三个：**自动触发、事件驱动、不依赖人工记忆。**

**【幻灯片 5：Skill vs Hook 快速判断】**

### 怎么区分什么时候用 Skill、什么时候用 Hook？

其实只需要问自己一个问题：

> 这件事是**用户主动发起**的，还是**某个事件发生时应该自动执行**的？

我给大家一张表：

| 如果你想解决的是…           | 更适合 |
|----------------------------|--------|
| 用户反复主动发起的复杂任务   | Skill  |
| 某类事件每次都该自动触发     | Hook   |
| 结果要有固定输出格式         | Skill  |
| 某个危险行为必须被拦截       | Hook   |

**【幻灯片 6：一个正例和一个反例】**

### 正例：把"修 bug"封装成 Skill

团队里每次修 bug 都希望 AI 按固定顺序做五件事：

1. 理解问题
2. 搜索相关代码
3. 实现最小修复
4. 补回归测试
5. 用固定格式总结根因和修改点

这非常适合做成 Skill。用户主动触发，输入是 bug 描述，输出是结构化修复报告。

### 反例：用 Skill 做"危险命令检查"

如果你把"禁止在 main 分支写文件"做成 Skill，那意味着用户必须记得每次主动调用 `/check-branch` 才行。问题是——一旦依赖人工记忆，这个约束迟早会失效。这种逻辑应该放在 Hook 里自动拦截，不给用户"忘了"的机会。

## 第三部分：为什么要做 Skills

**【幻灯片 7：从"会用"到"可重复"】**

OK，现在我们知道 Skill 和 Hook 分别是什么了。下一个问题是：为什么团队需要花时间来做这件事？

我先说一句话帮大家理清关系：

> **Rules 解决的是"AI 应该知道什么"，Skills 解决的是"AI 应该怎样稳定地做一类事情"。**

Rules 就像团队的公约，告诉 AI：我们用 TypeScript、我们的代码风格是这样、我们不允许做某件事。但 Rules 只是给 AI 设了边界，它不会帮你把"修 bug"这个流程编排成一条稳定的流水线。

而 Skills 就是在 Rules 的基础上，把高频操作变成一套固定流程。

**【幻灯片 8：没有 Skills 时的两个痛点】**

如果不做这层封装，团队会长期面临两个问题：

**痛点一：高质量做法只存在于少数人的聊天记录里。**

你团队里最会用 AI 的那个人，他的 prompt 技巧、流程设计、输出要求，全部藏在他自己的对话历史里。别人根本没法学，也没法复用。

**痛点二：每个人都在手写一套相似但不一致的操作流程。**

三个人做同一件事，三种不同的流程，三种不同质量的输出。这不只是效率问题，还是质量问题。

**Skills 的核心价值就是一句话：把"会用"变成"可重复"。**

打个比方：Skills 就像团队的 SOP——标准操作流程。只不过以前的 SOP 是给人看的，现在的 Skills 是给 AI 执行的。AI 会严格按你写的步骤来，不会偷懒也不会跳步。

## 第四部分：Skills 能做什么

**【幻灯片 9：基础能力——四类最常见的 Skill】**

讲完为什么要做，我们来看 Skills 到底能做到什么程度。我把它分成三个层次来讲。

### 基础能力

最容易上手的四类 Skill：

1. **Bug 修复标准化。** 每次修 bug 都按固定流程走：理解问题 → 搜索代码 → 最小修复 → 补测试 → 总结根因。输出格式统一，方便追踪和回顾。

2. **测试生成自动化。** 给定一段代码，自动生成单元测试。Skill 里定义好覆盖哪些场景、用什么测试框架、输出格式是什么样。

3. **代码 Review 规范化。** 让 AI 从安全性、性能、可读性、边界条件这几个维度来审代码，输出结构化的 review 报告。每次 review 的标准一致，不会因为人不同而标准不同。

4. **日报 / 周报模板化。** 每天结束时调一下 `/daily-report`，自动读取今天的 git commit、PR 记录、解决的问题，生成一份格式统一的工作日报。

**【幻灯片 10：进阶能力——七大设计模式】**

### 进阶能力

当你的 Skill 写得越来越多，就需要一些进阶技巧。这里介绍七个设计模式，来自社区开源项目 colleague-skill 的研究总结，每个模式解决一类实际问题。

**模式一：Skill 作为可分发的"产品包"。**

普通做法是 Skill 放在自己项目里只有自己用。进阶做法是把 Skill + 工具脚本 + 文档打包成独立仓库，通过 `npx skills add your-org/your-skill` 一键安装到任何项目。想象一下，团队 A 做了一个很好用的 review Skill，团队 B 只需要一条命令就能装到自己项目里。

**模式二：Prompt 微服务化架构。**

一个 Skill 写几百行什么都往里塞，这是最常见的反模式。更好的做法是把复杂 Skill 拆成多个子 prompt 文件，主文件只做编排。就像微服务一样，每个子 prompt 只负责一件事——信息采集、分析、生成、合并、纠正。好处是每个部分可以独立测试、独立优化，还能在不同 Skill 之间复用。

**模式三：用行为触发器代替形容词。**

这是最值得学的一个 Prompt 工程技巧。不要写"代码风格要简洁清晰"这种模糊描述。要写"函数体超过 50 行时，拆分为子函数并提取到独立文件"。公式是：**在[具体场景]时，[具体行为]。** 行为触发器比形容词精确十倍。

**模式四到七我就快速过一下——**

- **模式四：优先级规则显式化。** 当 Skill 有多个信息来源时，明确声明哪个优先——用户本次说的 > 项目 Rules > 现有代码风格 > Skill 默认规则。
- **模式五：增量追加机制。** 收到新信息时只追加不覆盖，标注冲突，等待人工确认。
- **模式六：纠正学习闭环。** 用户说"不对"时自动提取三要素——场景、错误行为、正确行为——记录到知识库。
- **模式七："无依据不推断"原则。** 对于需要高可信度的内容，没有依据就标注缺失，而不是编造。

**【幻灯片 11：组织级能力——让全部门用上 Skills】**

### 组织级能力

Skills 不只是研发的事。

当团队里还有产品经理、设计师和管理者时，常常会出现三个断层：

1. **安装断层**——非研发不知道怎么安装一个 Skill
2. **使用断层**——非研发不用命令行
3. **更新断层**——非研发积累了大量经验，但没有渠道沉淀回 Skill

怎么解决？按角色分层参与：

| 参与层级     | 含义                           | 适合角色         |
|-------------|-------------------------------|-----------------|
| **消费结果** | 不直接使用 Skill，享受标准化产出 | 管理者、协作方    |
| **使用 Skill** | 通过熟悉的界面触发 Skill       | 产品经理、设计师  |
| **维护 Skill** | 直接编辑 Skill 文件            | 研发、Tech Lead  |

非研发人员可以通过 Claude 网页端的 Project Instructions、Codex 桌面端的图形界面来直接使用 Skill，不需要学命令行。

同时，要建立**反馈通道**——非研发人员发现"AI 生成的需求文档总是漏掉权限边界"这种问题，按固定格式提交反馈，Tech Lead 审核后更新 Skill，全员受益。

## 第五部分：怎么做 Skills

**【幻灯片 12：四步实操法】**

### 第一步：先找对封装对象

不是所有操作都适合做成 Skill。最适合的是：**高频、固定格式、容易验证**的任务。

问自己三个问题：
- 这个操作每周至少做两次吗？
- 它有固定的输入和输出格式吗？
- 做完之后能很快判断对不对？

如果三个都是"是"，那它大概率适合做成 Skill。

### 第二步：让 Skill 文件结构足够稳定

一个实用 Skill 至少应该包含五个部分：

1. **适用场景说明**——什么时候该用这个 Skill
2. **输入参数**——用户需要提供什么信息
3. **推荐执行步骤**——AI 应该按什么顺序做
4. **输出格式**——最终产出应该长什么样
5. **限制条件**——什么情况下不该用

### 第三步：Hook 只做"自动且必要"的事

不要让 Hook 去做需要人工判断的事情。最适合第一批 Hook 的是：

- **SessionStart：** 会话开始时补充环境上下文
- **PreToolCall：** 调用工具前做风险拦截
- **PostToolCall：** 调用工具后做审计记录

### 第四步：先在一个最小项目里跑通

不要一上来就在复杂业务项目里设计十几个 Skill。先用一个小项目验证三件事：

- 命名是否清晰？
- 输入输出是否稳定？
- 是否真的节省了重复操作？

**【幻灯片 13：一个 Skill 长什么样】**

### Skill 文件结构

给大家看一个典型 Skill 的文件结构：

```text
fix-bug/
├── SKILL.md          # 主入口，编排整个流程
├── INSTALL.md        # 安装说明
├── prompts/          # 子 prompt 文件
│   ├── understand.md # 理解问题
│   ├── search.md     # 搜索代码
│   ├── fix.md        # 实现修复
│   └── summarize.md  # 总结输出
├── tools/            # 辅助脚本
└── README.md
```

主文件 `SKILL.md` 只做编排，每个子 prompt 专注一件事。这样做的好处是——每个部分可以独立调试，也可以被其他 Skill 复用。

**【幻灯片 14：安装与目录】**

### 安装与目录

安装现成 Skill：

```bash
npx skills add your-org/your-skill
```

团队共享目录推荐这样组织：

```text
.agents/
├── skills/
│   ├── engineering/    # 研发专用
│   │   ├── fix-bug.md
│   │   ├── gen-tests.md
│   │   └── review-code.md
│   ├── product/        # 产品专用
│   │   └── requirement-doc.md
│   ├── design/         # 设计专用
│   │   └── copy-review.md
│   └── shared/         # 跨角色共享
│       ├── meeting-summary.md
│       └── risk-assessment.md
```

为什么不放在 `.claude/commands/` 下？因为那是 Claude Code 的专属目录，如果团队未来还会用 Cursor、Copilot 或其他 AI 工具，放在 `.agents/skills/` 下更通用——它本质上就是 Markdown 文件，任何能读文件的 AI 工具都能加载。

**【幻灯片 15：最小落地路径】**

### 推荐的最小路径

1. 先做 1 个最常用的 Skill
2. 再做 1 个真正能拦住风险的 Hook
3. 跑 1–2 个迭代观察效果
4. 根据重复问题再扩充，而不是一开始就铺满

这比一开始就堆很多命令更稳，因为团队能更快判断哪些封装是真正有价值的。

**【幻灯片 16：常见反模式】**

### 避免这些坑

| 反模式                           | 为什么会出问题           |
|---------------------------------|------------------------|
| 一个 Skill 写几百行，什么都想管   | 很难维护，也很难复用      |
| Hook 做太多业务判断               | 自动化逻辑变得不可预测    |
| Skill 名字太抽象                 | 团队不知道什么时候该调用  |
| 把临时一次性流程沉淀成永久 Skill  | 只会制造噪音资产          |

**一句话判断标准：如果一个 Skill 很少被调用，或者团队根本说不清它何时适用，通常说明它不该存在。**

## 第六部分：目前有哪些好用的 Skills

**【幻灯片 17：Anthropic 官方 Skills 全览】**

### Anthropic 官方 Skills

Anthropic 自己维护了一套官方 Skill，都在 [anthropics/skills](https://github.com/anthropics/skills) 这个仓库里。我挑几个对我们团队最有用的讲一下。

**文档处理类：**
- **pdf**——PDF 全流程处理。读取、文字提取、合并拆分、表单填写、水印、加密，基本上 PDF 相关的操作都覆盖了。
- **docx**——Word 文档创建与编辑。支持从零新建，也支持编辑现有文档，包括批注和修订标记。
- **pptx**——PowerPoint 演示文稿。可以用数据自动生成汇报 PPT，按品牌模板批量出幻灯片。
- **xlsx**——Excel 电子表格。特别擅长财务模型场景，所有计算必须使用 Excel 公式，不会硬编码。

**开发工具类：**
- **frontend-design**——高质量前端界面生成。刻意避免"AI 生成感"的通用设计，强调有辨识度的配色、字体和版式。
- **mcp-builder**——MCP Server 开发指南。从调研到实现到测试的完整流程。
- **skill-creator**——Skill 开发脚手架。如果你想自建 Skill，从这个工具开始比从空白文件开始高效很多。
- **webapp-testing**——用 Playwright 自动化测试 Web 应用。

这些官方 Skill 的安装很简单，在 Claude Code 里可以通过 `/install-skill` 安装，在 Claude.ai 网页端可以在项目设置中添加。

**【幻灯片 18：社区 Skill Pack 三大流派】**

### 社区 Skill Pack

社区也涌现出了一些非常优质的 Skill Pack。这里重点介绍三个，它们代表了三种不同的思路：

**gstack——角色化 Skill Pack**

gstack 的思路是把 AI 从"什么都能做的万能助手"变成一支"虚拟工程团队"。它给每类工作绑定一个专业角色：

- `/office-hours`——CEO 视角，批判产品价值
- `/review`——Reviewer 角色，做 PR 代码审查
- `/qa`——QA 工程师，做端到端功能测试
- `/ship`——Release Manager，执行发布 Checklist
- `/cso`——安全官，做安全合规审查

日常开发最常用的就是 **`/review` → `/qa` → `/ship`** 这三步核心链路。

**superpowers——方法论驱动的工程流水线**

superpowers 的核心目标不是给你更多命令，而是让 AI 默认按工程化流程工作。它会强制 AI 先停下来：先搞清楚问题是什么，设计是否说清楚了，任务能不能拆成稳定的小步，每一步有没有验证方法。

它的主流程是：需求澄清 → 隔离开发环境 → 任务拆解 → 执行实现 → 测试驱动 → 代码审查 → 分支收尾。全程自动触发相关 Skill，用户不需要每一步都手动点名。

**GSD——上下文工程 / 规格稳定层**

GSD 解决的是一个很实际的问题：项目做久了以后，最初的目标、约束、决策和进度会逐渐"散掉"——官方叫 context rot。GSD 的做法是把这些信息拆成稳定工件：`PROJECT.md`、`REQUIREMENTS.md`、`ROADMAP.md`、`STATE.md`，持续维护，让 AI 在跨会话时始终知道自己为什么做、做到哪了、下一步该做什么。

**【幻灯片 19：三大 Skill Pack 选型】**

### 选型建议

| 你的需求                         | 推荐选择      |
|----------------------------------|--------------|
| 想要显式调用不同专家角色           | gstack       |
| 想要 Agent 默认按工程流程自动推进  | superpowers  |
| 长链路项目需要防止上下文漂移       | GSD（补充层） |

一个关键提醒：**不建议同时启用两套作为主编排层。** 它们都是强约束体系，如果同时开启，流程触发点会重叠，AI 不知道该优先遵循哪套方法。

更稳的做法是：选一套做主编排层，另一套只把少量设计思想吸收到自己的规则里。

## 第七部分：下一步行动

**【幻灯片 20：团队可以立即做的三件事】**

最后，我不想让今天的分享停在"听完就散"。我给大家三个可以立即动手的事情：

**第一件：选一个你每周至少做两次的操作，写成 Skill 草稿。**

不需要很复杂，写清楚五个部分就好：什么时候用、需要什么输入、按什么步骤做、输出什么格式、什么时候不适用。

**第二件：选一个你希望永远不要靠人工记住的安全提醒，写成 Hook 规则草稿。**

比如"不允许在 main 分支直接改文件"、"提交前必须通过 lint 检查"。

**第三件：把写好的 Skill 放到 `.agents/skills/` 给团队试用。**

写完后问自己两个问题：

- 团队其他人看到名字，能不能知道什么时候用？
- 如果以后项目变了，这个封装还能不能维护？

如果两个都是"能"，恭喜，你的第一个 Skill 就算成了。

**【幻灯片 21：总结回顾】**

今天这个分享讲了六件事：

1. 为什么我们需要 Skills——解决"会用 AI 但不可重复"的问题
2. Skills 是什么——主动工作流入口（Skill）+ 自动守门逻辑（Hook）
3. 为什么要做——把"会用"变成"可重复、可共享、可维护"
4. 能做什么——从基础的 bug 修复标准化，到进阶的七大设计模式，到组织级跨部门共享
5. 怎么做——找高频任务、稳定结构、最小起步、避免反模式
6. 有哪些好用的——Anthropic 官方 Skills + 社区 gstack / superpowers / GSD

最核心的一句话：**Skills 的价值不在于你有多少个 Skill，而在于你封装了多少个"真正被反复使用、持续维护的稳定工作流"。**
