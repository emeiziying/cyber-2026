# Skills 团队分享——提纲

> 预计时长：40–50 分钟（含互动）
> 目标听众：团队全员（研发 + 产品 + 设计 + 管理者）
> 分享目标：让团队理解 Skills 是什么、为什么要做、怎么做、有哪些现成可用的，并在分享结束后能迈出第一步

---

## 第一部分：为什么要聊 Skills（5 分钟）

- 开场痛点：AI 工具用起来了，但新的低效开始出现
  - 同一种 bug 修复说明要反复说
  - 同一种 review 格式每次都要重复要求
  - 高质量做法只存在于少数人的聊天记录里
  - 每个人都在手写一套相似但不一致的操作流程
- 核心命题：如何把"会用 AI"变成"可重复、可共享、可维护"

---

## 第二部分：Skills 是什么（10 分钟）

### 2.1 Skill 的定义

- Skill = 带说明的主动工作流入口
- 把用户主动发起的复杂流程封装起来
- 典型例子：修 bug、生成测试、做 code review、产出日报
- 调用方式：Claude 用 `/skill-name`，Codex 用 `$skill-name`

### 2.2 Hook 的定义（对比理解）

- Hook = 事件发生时自动执行的守门逻辑
- 无需用户主动提醒
- 典型例子：会话开始加载环境信息、拦截危险命令、记录修改日志

### 2.3 Skill vs Hook 快速判断

| 如果你想解决的是…         | 更适合 |
|--------------------------|--------|
| 用户反复主动发起的复杂任务 | Skill  |
| 某类事件每次都该自动触发   | Hook   |
| 结果要有固定输出格式       | Skill  |
| 某个危险行为必须被拦截     | Hook   |

### 2.4 一个正例和一个反例

- 正例：把"修 bug"封装成 Skill
- 反例：用 Skill 做本该自动触发的守门逻辑

---

## 第三部分：为什么要做 Skills（5 分钟）

- Rules 解决"AI 应该知道什么"，Skills 解决"AI 应该怎样稳定地做一类事情"
- 没有封装时的两个问题：
  1. 高质量做法只存在于少数人的聊天记录里
  2. 每个人都在手写一套相似但不一致的操作流程
- Skills 的核心价值：把"会用"变成"可重复"
- 类比：Skills 就像团队的 SOP，只不过执行者是 AI

---

## 第四部分：Skills 能做什么（8 分钟）

### 4.1 基础能力

- bug 修复标准化（固定流程 + 固定输出格式）
- 测试生成自动化
- 代码 review 规范化
- 日报/周报模板化

### 4.2 进阶能力——七大模式

- 模式一：Skill 作为可分发的"产品包"（npx skills add）
- 模式二：Prompt 微服务化架构（拆分子 prompt）
- 模式三：用行为触发器代替形容词（精确规则）
- 模式四：优先级规则显式化（信息冲突时的决策）
- 模式五：增量追加机制（只追加、不覆盖）
- 模式六：纠正学习闭环（用户反馈持续优化）
- 模式七："无依据不推断"原则（高可信度输出）

### 4.3 组织级能力

- 跨部门 Skill 共享（研发、产品、设计都能参与）
- 非研发人员的使用路径（Claude 网页端 / 桌面端工具）
- 反馈通道：非研发经验也能沉淀回 Skill

## 第五部分：怎么做 Skills（8 分钟）

### 5.1 四步实操法

1. 先找高频、固定格式、容易验证的任务
2. 让 Skill 文件结构足够稳定（场景说明 + 输入参数 + 执行步骤 + 输出格式 + 限制条件）
3. Hook 只做"自动且必要"的事
4. 先在一个最小项目里跑通

### 5.2 一个 Skill 长什么样（结构示例）

```text
your-skill/
├── SKILL.md          # 主入口（主编排文件）
├── INSTALL.md        # 安装说明
├── prompts/          # 子 prompt 文件
│   ├── step1.md
│   └── step2.md
├── tools/            # 辅助脚本
└── README.md
```

### 5.3 安装与目录建议

- 默认用 `npx skills add <owner>/<repo>` 安装
- 团队共享目录：`.agents/skills/`
- 分角色组织：engineering / product / design / shared

### 5.4 最小落地路径

1. 先做 1 个最常用的 Skill
2. 再做 1 个真正能拦住风险的 Hook
3. 跑 1–2 个迭代观察效果
4. 根据重复问题再扩充

### 5.5 常见反模式

| 反模式                         | 为什么会出问题     |
|-------------------------------|-------------------|
| 一个 Skill 写几百行            | 很难维护和复用     |
| Hook 做太多业务判断             | 自动化变得不可预测 |
| Skill 名字太抽象               | 团队不知道何时调用 |
| 把临时一次性流程沉淀成永久 Skill | 制造噪音资产       |

## 第七部分：下一步行动（3 分钟）

### 团队可以立即做的三件事

1. 选一个你每周至少做两次的操作，写成 Skill 草稿
2. 选一个你希望永远不要靠人工记住的安全提醒，写成 Hook 规则草稿
3. 把写好的 Skill 放到 `.agents/skills/` 给团队试用

### 验证问题

- 团队其他人看到名字，能不能知道什么时候用？
- 如果以后项目变了，这个封装还能不能维护？
