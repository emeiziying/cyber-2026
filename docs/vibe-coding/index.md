# Vibe Coding

> **适合人群：** 工程师
> **学习目标：** 理解外部语境里 `vibe coding` 大致指什么、它适合什么场景，以及在真实工程里如何把这种“先试起来”的方式收束成可控协作

---

## 本章解决什么问题

`Vibe Coding` 这个词流行之后，团队里很容易出现两种误读：

- 一种是把所有“用 AI 写代码”的行为都叫作 vibe coding
- 另一种是因为它听起来“不严肃”，就直接否定 AI 协作本身

这两种理解都不够准确。

本章真正要解决的是：**什么情况下可以先“顺着感觉把东西跑起来”，什么情况下必须立刻切回可控协作与工程约束。**

---

## 为什么这件事重要

外部讨论里，`vibe coding` 更接近一种低约束、低解释成本的 prompt 驱动式写法：先把东西做出来，再看结果。

这种方式在原型验证、一次性脚本、低风险探索中很有价值，因为它能把想法快速变成可运行结果。  
但如果把这种工作方式直接带进真实工程，就会出现三个问题：

- 目标和边界说不清，结果越来越漂
- 改动能跑，但没人真正理解为什么能跑
- 没有验证和约束，错误会被更快放大

所以关键不在于“要不要 vibe”，而在于**能不能识别它什么时候有用、什么时候该停。**

---

## 核心概念与边界

### 外部语境里的 Vibe Coding

更接近外部公开讨论的 `vibe coding`，通常有这些特征：

- 用自然语言快速驱动 AI 生成代码或原型
- 人更关注“先看到结果”，而不是一开始就逐行理解实现
- 适合低风险、可丢弃、可快速观察结果的任务

如果一段代码已经被认真 review、测试、理解，并且准备进入长期维护，它通常就不再是狭义上的 `vibe coding`，而更接近正常的 AI 辅助开发。

### 工程里更稳妥的做法

真实工程里，常见的更稳妥路径不是“完全不要 vibe”，而是：

1. 用直觉式输入快速起一个方向
2. 一旦要动真实代码，就补目标、上下文、约束和验收
3. 让 AI 先解释计划，再决定是否放行修改
4. 用验证和 review 把结果收回来

也就是说，本章更关心的是：**怎样把 vibe 式起手，收束成可控协作。**

### 什么时候可以先用 vibe 起手

下面这些场景通常可以先用较松的方式推进：

- 内部 demo 或一次性原型
- 低风险的界面草图、文案试写、脚本试验
- 可以很快运行、很快观察、很快推翻重来的探索

### 什么时候不能停在 vibe

只要出现下面任一特征，就不该继续停在“纯 vibe”状态：

- 涉及权限、认证、安全、支付、数据迁移
- 代码会进入长期维护的生产仓库
- 失败后不容易立即发现
- 没有测试保护，或者你无法解释关键逻辑

## 一个最小场景与反例

### 正例：先做一个低风险原型

```text
先帮我做一个内部 demo 页面，只用假数据：
- 验证“搜索 + 筛选 + 空态提示”这套交互是否顺手
- 不接真实接口
- 不进正式路由
- 能本地跑起来给我看就行
```

这个输入适合先用较松的方式推进，因为它同时具备：

- 目标明确：验证交互方向
- 风险较低：不接真实数据和权限
- 可快速观察：页面跑起来就能判断方向
- 可丢弃：不要求直接进入长期维护

### 反例：把生产改动也当原型处理

```text
帮我把现有搜索做好一点，顺便一起优化一下列表体验。
```

这类输入的问题不是短，而是它同时缺了三样关键东西：

- 没有定义什么叫“更好”
- 没有说明哪些既有行为不能变
- 没有给出验收方式

一旦任务进入真实工程，这种输入就很容易把“快速起步”变成“快速失控”。

---

## 实操方法：把 vibe 式起手收束成可控协作

### 第 1 步：先判断这是不是低风险探索

先问自己两个问题：

- 这次产出是不是允许被推翻？
- 即使 AI 理解错了，成本是不是也很低？

如果两个答案都是否定的，就不要按纯 vibe 方式推进。

### 第 2 步：补上最小工程信息

一旦准备动真实代码，至少补这五类信息：

```text
目标 + 上下文 + 约束 + 输出形式 + 参考材料
```

### 第 3 步：让 AI 先解释计划

在真正改动前，先要求 AI 说明：

- 打算改哪些文件
- 为什么这么改
- 哪些地方最可能有风险

### 第 4 步：要求验证和总结

完成后不要只看 diff，还要追问：

- 你做了哪些验证
- 哪些边界还没覆盖
- 如果我只 review 一处，最该看哪里

这一步的意义，是把“先跑起来”收束到“能解释、能验证、能放行”。

---

## 什么时候退出 Vibe 模式

出现下面任一信号，都应该切回更精确的控制方式：

1. AI 连续两到三轮都没有理解核心问题
2. 需求里出现权限、安全、兼容性或高风险边界
3. 你已经无法解释它生成的关键逻辑
4. 改动开始影响核心模块，却还没有测试保护
5. 你发现自己在不断“补一句再试一次”，但目标仍然不清楚

**结论：**  
退出 Vibe 模式不是失败，而是说明任务已经进入需要更高确定性的阶段。

## 常见误区 / 风险提醒

| 误区 | 更稳妥的做法 |
|------|--------------|
| “只要用了 AI 写代码，就都叫 vibe coding” | 区分低风险原型和可维护工程，别把所有 AI 协作混成一个词 |
| “vibe coding 天生不严肃，所以没必要学” | 真正要学的是如何识别它的适用边界，并及时收束 |
| “第一版跑起来就算完成” | 必须继续追问边界、测试和未覆盖风险 |
| “AI 已经写了，所以我不需要理解” | 理解不了的关键逻辑，默认不能直接放行 |

**风险提醒：**  
`Vibe Coding` 最容易让人上头的地方，是前两轮看起来进展很快；真正的质量差异通常出现在收束、验证和验收阶段。

## 最小练习

选一个你熟悉的小任务，做两次输入对照：

1. 先用一句很松的原型式描述，让 AI 起一个低风险版本
2. 再把同一个任务改写成“目标 + 上下文 + 约束 + 输出形式 + 参考材料”
3. 让 AI 先说计划，不直接写代码
4. 最后比较两次输出在可解释性和可验证性上的差别

如果你能清楚看出第二种方式更适合真实工程，就已经掌握了本章最关键的判断。
