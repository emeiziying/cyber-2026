# Agentic Coding：从对话协作到委派执行

## 背景

随着 Claude Code、Codex、Cursor 这类工具逐步具备文件读写、命令执行、浏览器控制和外部工具调用能力，很多团队会自然问出一个问题：

**既然工具已经“像 Agent”了，我们是不是应该直接进入 Agentic Coding？**

更稳的回答是：不一定。  
工具能力的演进，让委派式执行变得可行；但 `agentic` 这个词真正描述的，不是某个产品按钮，而是一种**工作方式**：

- 人把目标、边界、验收标准先说清楚
- AI 不再按轮次被动响应，而是自主规划并执行多步任务
- 人的主要工作从“每轮纠偏”转向“授权、检查点控制、最终验收”

所以这页的重点不是“某个工具算不算 agentic”，而是**怎样判断一次协作是否已经更接近委派式执行。**

## 先拆开：工具能力和工作方式不是一回事

把 `Vibe Coding` 和 `Agentic Coding` 混为一谈，通常是因为把两个维度写成了一个问题。

### 维度一：人类介入密度

| 工作方式 | 典型状态 |
|----------|----------|
| 对话协作 | 你一轮、AI 一轮；你频繁补约束、看计划、纠偏 |
| 委派执行 | 你先定义目标和边界，AI 连续做多步，关键节点再回来汇报 |

### 维度二：模型执行自治度

| 执行能力 | 典型状态 |
|----------|----------|
| 低自治 | 主要生成文本或局部代码，几乎不主动观察结果 |
| 高自治 | 会读写文件、跑命令、调工具、看结果、再决定下一步 |

把这两个维度叠在一起，就能得到更稳的判断：

- **不是所有对话式协作都该叫 vibe**
- **也不是所有具备工具能力的产品都天然处在 agentic 模式**

同一个 Claude Code，会因为你的任务描述、权限设置、验收要求不同，而表现得更像“互动式协作”或“委派式执行”。

## 同一个工具里，两种用法都可能发生

### 更接近互动式协作

```text
先不要改文件。
帮我分析这个 bug 可能和哪些文件有关，列出计划和风险点，等我确认后再动手。
```

这个任务里，工具虽然有改文件和跑命令的能力，但你并没有把执行权完整委派出去。  
你仍然在按轮次主导过程。

### 更接近委派式执行

```text
请在 `src/features/orders/**` 范围内完成这次修复：
- 目标：修复订单列表分页失效
- 不能改：鉴权、接口协议、埋点
- 验收：相关测试通过，`pnpm typecheck` 通过
- 如果需要扩大范围或碰到权限逻辑，先停下来汇报
```

这个任务里，你给的是一份可执行的委派说明。  
AI 可以自己找文件、改实现、跑验证，再把结果交回来。

**关键点：**  
区分 `vibe` 和 `agentic` 的，不是有没有一个模式开关，而是你有没有把“多步执行权”真正委派出去，以及你是否给了足够的边界和验收。

## 一个对比场景

同一个任务：“给现有 REST API 补充分页功能”。

### 更接近互动式协作

```text
第 1 轮：描述需求——给列表接口加分页，用 offset + limit
第 2 轮：补约束——保持返回格式兼容，默认 limit=20，最大 100
第 3 轮：要方案——先列出要改的文件和改法
第 4 轮：确认方案后，再逐步实现并验证
```

### 更接近委派式执行

```text
一次性任务描述：
- 目标：给所有列表接口加分页
- 约束：offset + limit 参数，默认 20，最大 100，保持返回格式兼容
- 验收：现有测试通过，新增分页测试覆盖边界情况
- 不能改：认证和权限逻辑

AI 自主完成：
1. 扫描代码库，找到所有列表接口
2. 分析现有返回格式
3. 设计通用分页方案
4. 逐个接口实现修改
5. 补充测试
6. 运行全部测试，修复失败项
7. 输出改动摘要
```

两种方式都可以由同一个工具完成。  
区别只在于：前者是你在过程中持续主导，后者是你把执行闭环委派了出去。

## 什么时候更适合委派式执行

下面这些条件同时满足得越多，就越适合往 `agentic` 方向走：

- **目标清楚**：知道要交付什么，而不是边做边讨论方向
- **边界清楚**：知道哪些文件能动、哪些行为不能变
- **验收清楚**：能用测试、构建、检查项或明确 review 点判断完成与否
- **权限可控**：能限制写目录、危险命令和高风险模块
- **任务有多步闭环**：需要搜索、修改、验证、再调整，而不是一次输出就结束

## 什么时候不要急着上 Agentic

下面这些场景，即使工具有能力，也不建议直接按 `agentic` 委派：

- 方向还在探索，需要频繁与人讨论取舍
- 涉及权限、安全、支付、数据库迁移等高风险逻辑
- 业务规则复杂，但没有测试保护
- 你自己都还说不清“做完以后怎么验收”
- 团队没有基本的 Rules、测试和 CI，出错后难以及时收回来

## 一个更实用的判断框架

```text
任务是否有明确验收标准？
  ├─ 否 → 不适合直接委派，先保持互动式协作
  └─ 是 → 是否仍需要频繁讨论方向和取舍？
           ├─ 是 → 先用互动式协作，把方向收敛
           └─ 否 → 是否具备测试、规则和权限边界？
                    ├─ 否 → 先补 Harness，再扩大委派
                    └─ 是 → 可以尝试委派式执行
```

这个判断框架比“工具有没有 agent 模式”更重要。

## 委派式执行带来的新风险

### 隐蔽的回归

AI 连续修改多个文件时，可能在不经意间改变已有行为。  
对话模式下你每一轮都在看；委派模式下，很多变化会在你最后一次性看到。

### 上下文漂移

长时运行的任务容易逐渐偏离最初目标。  
如果没有检查点和暂停条件，AI 可能会“越修越远”。

### 权限过大

当 AI 同时拥有文件读写、命令执行和外部工具访问能力时，错误会被更快放大。  
能力越强，越要控制授权边界。

### 伪完成

最常见的问题不是“完全做错”，而是“看起来像完成了”，但测试没覆盖关键路径、关键文件没 review、验收条件也没有真正落实。

## 实践要点

### 不要问“这个工具算不算 agentic”

更有用的问题是：

- 这次任务是不是在做委派？
- 我给的边界够不够？
- 这个任务是否可自动验收？
- 如果它走偏了，什么时候该停下来？

### 前置约束比过程干预更重要

一旦你把多步执行权委派出去，最重要的就不再是“中途多说一句”，而是：

- `AGENTS.md` 里的规则是否清楚
- 测试和检查是否足以验证结果
- 停止条件是否明确
- 高风险区域是否被限制

### 从小任务开始扩大委派

更稳的路径通常是：

1. 先委派单文件或低风险测试补充
2. 再委派跨两三个文件的小重构
3. 等规则、验收和权限边界跑顺后，再扩大到端到端任务

## 小结

`Agentic Coding` 不是“更高级的工具模式”，而是**更高委派度的协作方式**。

工具演进让它变得可行，但真正决定它能不能稳定工作的，是：

- 任务是否可委派
- 验收是否可执行
- 权限是否被限制
- 团队是否具备基本的 Harness

所以，从 `Vibe` 到 `Agentic` 不是“换一个按钮”，而是从“互动式协作”逐步走向“委派式执行”。
