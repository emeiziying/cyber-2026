# 如何制作 Skills

> **适合人群：** 已经理解 Skill / Hook 基本区别，准备做第一个可复用、可迁移 Skill 的读者
> **目标：** 知道如何先把 Skill 做成宿主无关的源文件，再按需要接入 Claude、Codex 等不同宿主

---

## 这页解决什么问题

这一页**不再重复解释**“什么时候该用 Skill、什么时候该用 Hook”。  
这些判断已经在 [Skills & Hooks 主章](./) 里讲过了。

这里默认你已经完成了两件事：

- 已经确认这件事值得沉淀成 Skill
- 已经确认它不是更适合放进 Hook 或子 Agent 的问题

在这个前提下，这页只解决制作问题：

- 通用 Skill 的最小形态应该长什么样
- 哪些内容应该属于 Skill 本体，哪些只是宿主适配层
- 一个 Skill 先写到什么程度就够用
- 什么时候再考虑共享、分发、Skill Pack 化

它的目标不是帮你“判断要不要做”，而是帮你“把第一个 Skill 做对”。

---

## 先做通用 Skill，再接到具体宿主

### 通用 Skill 的核心形态

无论你最后把 Skill 接到 Claude、Codex 还是其他宿主，先写出来的都应该是一份**宿主无关的 Skill 源文件**。

更稳的默认形态是目录式组织：

```text
my-skill/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

最小可用版本只需要 `SKILL.md`；其余内容按需添加：

- `scripts/`：需要确定性执行的辅助脚本
- `references/`：只在必要时加载的大段参考资料
- `assets/`：模板、图标、字体等输出资源

这部分才是 Skill 的**本体**。  
它解决的是“能力如何被定义”，而不是“某个产品如何发现它”。

### 宿主适配是第二层，不是第一层

当你需要把 Skill 接到具体宿主时，再补宿主适配层：

- 在 Claude 里，常见是把它接到官方 Skills 目录，或根据需要拆成命令入口 / 子 Agent
- 在 Codex 里，可以继续使用同一份 Skill 目录；如果要更好的界面展示，再补宿主自己的元数据文件
- 在其他宿主里，也应该尽量围绕同一份 `SKILL.md` 源文件做映射，而不是重写一份新的 Skill

关键原则是：

- **Skill 本体尽量保持通用**
- **宿主专属目录、frontmatter 字段、界面元数据只作为适配层**
- **不要把某个工具的目录结构当成 Skill 唯一真实形态**

### 两边的共同点

无论最后接到哪个宿主，决定 Skill 是否好用的核心都不是目录名，而是前面的元信息：

- 名字是否清楚
- `description` 是否把“什么时候该用”说清楚
- 正文是否只保留真正会影响行为的步骤和约束

所以，**先把触发条件写对，比先把正文写长更重要。**

## 一个够用的最小 Skill 长什么样

第一版不要追求复杂目录，先把一个“会被正确触发、能稳定输出”的最小 Skill 做出来。

```text
fix-bug/
└── SKILL.md
```

`SKILL.md` 可以先从这种最小骨架开始：

```markdown
---
name: fix-bug
description: 在用户描述 bug、报错、失败测试、异常回归时使用。先定位根因，再做最小修复，并补一个回归验证。不适合大范围重构或全新功能设计。
---

收到问题后按这个顺序工作：

1. 先复述现象、影响范围和复现条件。
2. 搜索相关代码、日志和最近改动，确认根因。
3. 只做最小修复，不顺手重构无关部分。
4. 补一个最贴近故障面的验证。
5. 输出：根因、修改点、验证结果、剩余风险。
```

这就已经够做第一轮测试了。

如果某个宿主要求额外字段，比如禁自动调用、界面展示元数据或注册文件，那都属于**宿主适配层**，不是通用 Skill 第一版的必需项。

## 确定要做 Skill 之后，按这个顺序制作

### 第一步：先决定它怎么被触发

Skill 最常见的问题不是“内容不够多”，而是“根本不该触发时触发了，或者该触发时没触发”。

所以先写清楚：

- 什么场景下应该用
- 什么场景下不要用
- 是让模型自动触发，还是只允许人工显式调用

如果这一步没写清楚，后面正文写得再长，效果也不会稳定。

### 第二步：再做宿主适配

先把通用 Skill 本体写清楚，再决定怎么接到具体宿主。

常见适配方式包括：

- 作为宿主原生 Skill 目录的一部分
- 映射成宿主自己的 command 入口
- 在需要独立上下文、独立角色或独立工具权限时，改做子 Agent / 独立 Agent

这一层如果选错，后面经常会出现两种问题：

- 明明做的是通用 Skill，却被锁死在某个工具专属目录里
- 明明更适合独立 agent 的能力，却被硬塞成 Skill

### 第三步：正文只写最小流程

第一版正文只需要覆盖四类信息：

- 输入是什么
- 步骤按什么顺序走
- 输出要长什么样
- 明确不能做什么

不要一上来就塞进：

- 大量背景介绍
- 冗长理论解释
- 多套可选流程
- 与当前任务无关的知识库

正文越胖，触发后越容易把上下文挤满，反而让 Skill 更不稳。

### 第四步：只在需要时加配套文件

当 `SKILL.md` 已经写清楚，但还出现下面这些情况时，再拆文件：

- 需要确定性执行的步骤：放进 `scripts/`
- 需要大量参考资料：放进 `references/`
- 需要模板、图标、样式文件：放进 `assets/`

无论接到哪个宿主，原则都一样：**主文件负责导航和编排，详细资料按需加载。**

### 第五步：用 2-3 条真实提示词做回放测试

最小测试不要设计成“证明它很好”，而要设计成“暴露它会不会乱触发”。

至少准备三类提示词：

1. 明显应该触发的
2. 容易混淆、但其实不该触发的
3. 触发后最容易输出跑偏的

如果测试后发现：

- 该触发时没触发：收紧或前置 `description` 的关键场景
- 不该触发时触发了：把“不适用场景”写得更明确
- 触发了但输出不稳：缩短正文，强化输出格式和边界

### 第六步：跑顺了之后，再决定要不要共享

只有当它已经稳定可用时，才值得继续做共享、版本化和 Skill Pack 化。

## 写 Skills 时最常用的三条原则

### 用触发条件和动作，代替空泛形容词

比起写“回复要专业”“代码要简洁”，更有效的是直接写出触发条件和动作：

- 看到失败测试时，先定位失败断言和相关代码，再决定是否修改实现
- 用户只要求最小修复时，不扩展成重构任务
- 输出结论时，先给根因，再给修改点，最后给验证结果

这种写法更容易被模型执行，也更容易被团队维护。

### 把信息优先级写出来

如果一个 Skill 同时会受用户要求、项目规则、代码现状和默认做法影响，最好把优先级直接写出来，例如：

1. 用户这次明确指定的要求
2. 项目里的 AGENTS.md / CLAUDE.md / 规则文件
3. 代码库现有风格和约束
4. Skill 的默认做法

这样能减少模型在冲突信息之间自己猜测。

### 对高可信内容坚持“无依据不推断”

如果 Skill 会生成规范、档案、评审结论或对外说明，正文里最好明确写上：

- 只写有依据的内容
- 没有依据就标注缺失
- 不要为了“写满”而补推断

这条规则对文档类、评审类、知识库类 Skill 尤其重要。

## 什么时候再升级为共享资产

先把本地 Skill 跑通，再考虑共享和分发。

更适合进入“共享资产”阶段的信号是：

- 同一个 Skill 已经在两个以上项目里复用
- 团队里有人明确负责维护它
- 你已经有 2-3 条稳定的测试提示词
- 你已经知道哪些配套文件必须一起分发

到了这一步，再去考虑：

- 是否抽成独立仓库
- 是否做版本化管理
- 是否通过 `skills.sh` 或其他方式分发
- 是否把多个 Skill 组织成 Skill Pack

顺序不要反过来。  
**先验证它能不能稳定节省重复劳动，再决定要不要产品化。**
