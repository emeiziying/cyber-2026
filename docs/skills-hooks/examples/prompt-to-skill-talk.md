# 团队技术分享：从 Prompt 到 Skill，把 AI 使用习惯升级为团队能力

> **定位：** 这是一份面向混合团队的 45–60 分钟内部技术分享用稿，目标是帮助团队讲清 Skill 是什么、能做什么、为什么要做、如何制作，以及怎样把它变成团队能力。  
> **用法：** 可直接作为 PPTX 的逐页底稿。每一页都给出标题、建议时长、版式建议、页内内容和讲稿。

---

## 先用这份讲稿怎么讲

- 推荐时长：50 分钟内容 + 10 分钟 Q&A
- 推荐对象：研发、产品、设计、项目负责人、团队管理者混合听众
- 推荐口径：宿主无关，只把 Claude 的 `/skill-name` 或 Codex 的 `$skill-name` 当成入口示例
- 推荐目标：让非研发听懂价值，让工程同学带走最小做法，让团队负责人看到落地路径

| 阶段 | 页码 | 目标 | 推荐时长 |
|------|------|------|----------|
| 开场与问题定义 | P1–P3 | 先把“为什么今天讲 Skill”讲透 | 7 分钟 |

## 开场：先让团队知道这不是一场工具介绍

### P1｜从 Prompt 到 Skill，把 AI 使用习惯升级为团队能力

- 建议时长：1 分钟
- 页面目标：先把分享主题和结论立住，让听众知道这场分享不只是“介绍几个命令”
- 版式建议：深色封面页，左侧大标题，右侧用一条从 `Prompt → Skill → Team Capability` 的进阶箭头
- 页内内容：
  - 主标题：从 Prompt 到 Skill，把 AI 使用习惯升级为团队能力
  - 副标题：面向混合团队的 Skill 方法、案例与落地路径
  - 受众：研发 / 产品 / 设计 / 管理者
  - 一句话结论：真正值得做的，不是“更多 prompt”，而是“更稳定的工作流入口”
- 讲稿：

> 这一页先做一件事：把今天的主题讲清楚。我们不是来盘点工具菜单，也不是来演示几个花哨命令，而是想回答一个更实际的问题：当团队已经开始稳定使用 AI 之后，怎样把零散的高质量做法，升级成别人也能复用、组织也能维护的能力。今天的关键词就是 Skill。它不是一个更长的 prompt，而是把重复、稳定、可验证的工作流沉淀下来，让它成为团队资产。接下来我会先讲为什么要做，再讲边界、方法、案例，最后落到团队怎么开始。

### P2｜团队已经会用 AI，但高质量做法还停留在聊天记录里

- 建议时长：3 分钟
- 页面目标：用共性痛点建立共鸣，让不同角色都觉得这件事和自己有关
- 版式建议：左右双栏。左边放四个痛点卡片，右边放“临时提示词驱动”的失控链条
- 页内内容：
  - 痛点 1：同一种流程要反复解释
  - 痛点 2：同一种任务每个人做法都不一样
  - 痛点 3：经验只存在于少数人的脑子里和聊天记录里
  - 痛点 4：本该自动守住的风险仍然靠人工提醒
  - 结论：团队已经会“用 AI”，但还没把“高质量做法”变成稳定能力
- 讲稿：

> 这一页要解决的问题是，为什么今天要专门聊 Skill。很多团队现在其实已经会用 AI 了，但新的低效也跟着出来了。比如同一种 bug 修复流程，每次都要重新交代一遍；同一种文档写作任务，不同人做出来的质量和结构差异很大；再比如某些风险动作明明应该自动阻止，最后还是靠人盯着提醒。表面看，这像是“提示词还不够完整”；本质上，它说明高质量做法还停留在个人经验层，没有变成可复用的组织能力。Skill 要解决的，就是这层断裂。

### P3｜Skill 的本质，是把临场技巧升级为可复用工作流

- 建议时长：3 分钟
- 页面目标：在所有细节展开之前，先给出整场分享的总判断
- 版式建议：做一张 before / after 对照。左边是“一次性 prompt”，右边是“可复用 Skill”
- 页内内容：
  - Before：每次会话都从头解释
  - After：固定触发条件、固定步骤、固定输出
  - Before：只有会写 prompt 的人能稳定做出来
  - After：任何人都能通过统一入口复用
  - 一句话定义：Skill 是带说明的主动工作流入口
- 讲稿：

> 如果今天只记住一句话，我希望大家记住这一句：Skill 的本质，是把临场技巧升级成可复用的工作流入口。它和一次性 prompt 最大的区别，不是字数多少，而是它有没有稳定的触发条件、步骤顺序、输出格式和适用边界。临时 prompt 解决的是“一次怎么做”；Skill 解决的是“这类事以后都怎么稳定做”。这也是为什么 Skill 的价值不只在提效，它真正改变的是协作方式。

## 概念与边界：先把 Skill 放回正确位置

### P4｜Skill 不是更长的 Prompt，也不是另一套项目规则

- 建议时长：3 分钟
- 页面目标：先消掉两个最常见误解，避免后面越讲越混
- 版式建议：做三栏对比卡片，分别放 `Prompt`、`Skill`、`Rules`
- 页内内容：
  - Prompt：围绕当前一次请求临时组织表达
  - Skill：把一类主动任务封装成可复用流程
  - Rules：定义项目边界、优先级和禁区
  - Skill 不替代用户目标，也不替代项目规则
  - 结论：Skill 负责“怎样稳定做”，Rules 负责“什么不能错”
- 讲稿：

> 这一页是为了避免两个常见误区。第一个误区是把 Skill 理解成“更长的 prompt”；第二个误区是以为有了 Skill，就不需要项目规则。其实不是。Prompt 是为当前这次对话服务的，Skill 是把一类高频任务固定下来，Rules 则定义边界、优先级和禁区。更准确地说，Prompt 决定这次具体要什么，Rules 决定什么不能违反，Skill 决定这类事以后怎样稳定地做。三者是分工关系，不是替代关系。

### P5｜Rule、Skill、Hook、Agent 各自解决不同层级的问题

- 建议时长：4 分钟
- 页面目标：讲清四者分工，让团队知道什么时候停在 Skill，什么时候继续升级
- 版式建议：二维矩阵。横轴是“主动触发 / 自动触发”，纵轴是“局部任务 / 长链路任务”
- 页内内容：
  - Rule：定义边界和约束
  - Skill：封装用户主动发起的高频工作流
  - Hook：在特定事件发生时自动执行守门逻辑
  - Agent：处理跨阶段、跨上下文、需要更强自主性的复杂任务
  - 结论：先别急着做 Agent，很多问题停在 Skill 或 Hook 更稳
- 讲稿：

> 这一页要解决的是边界问题。很多团队一开始会把所有能力升级冲动都指向 Agent，但其实大部分问题不需要这么重。Rules 管的是边界；Skill 管的是用户主动发起、但又反复出现的复杂任务；Hook 管的是某个事件一发生就该自动执行的守门逻辑；Agent 才是用来处理跨阶段、跨上下文、需要长期自主推进的复杂任务。一个简单判断是：如果用户要主动叫它进场，多半先想 Skill；如果这件事每次都该自动发生，多半先想 Hook；如果它已经超出单次流程，需要长期保持状态，再考虑 Agent。

## 价值与方法：让团队知道为什么值得做，以及怎么起步

### P6｜Skill 最适合承接高频、主动发起、需要固定输出的任务

- 建议时长：3 分钟
- 页面目标：让听众对“Skill 能做什么”形成可操作的任务画像
- 版式建议：四象限任务分组图，不按工具分，而按任务类型分
- 页内内容：
  - 工程类：修 bug、补测试、做 code review
  - 文档类：写需求、整理日报、生成发布说明
  - 分析类：竞品分析、问题排查、风险评估
  - 协作类：会议纪要、交接说明、验收总结
  - 共性特征：主动触发、流程相对稳定、输出有明确形状
- 讲稿：

> 这一页要回答“Skill 到底能做什么”。更稳的看法不是按宿主菜单分类，而是按任务类型分类。只要一类任务同时满足三个条件，它就很适合做成 Skill：第一，用户会反复主动发起；第二，执行过程相对稳定；第三，输出结果有比较明确的形状。修 bug、补测试、写需求、做竞品分析、生成会议纪要都属于这类。换句话说，Skill 最适合承接那些你每周都会重复做、而且好坏标准已经比较清楚的工作。

### P7｜做 Skill 的收益，不只是提效，而是让经验变成团队资产

- 建议时长：3 分钟
- 页面目标：把价值从“个人效率”上升到“团队协作”和“组织治理”
- 版式建议：中间放“团队资产化”，四周放四个收益点
- 页内内容：
  - 复用：减少重复解释
  - 稳定：减少风格漂移和步骤遗漏
  - 协作：让不同角色站在同一条流程起跑线上
  - 传承：把少数人的经验变成团队可继承能力
  - 治理：更容易挂接反馈、评估和后续维护
- 讲稿：

> 如果把 Skill 只理解成“更快完成任务”，它的价值会被低估。它真正重要的地方是，让经验从个人习惯变成团队资产。高质量做法不再只存在于某几个人的聊天记录里，而是可以被复用、被审视、被迭代、被继承。对研发来说，它减少重复解释；对产品和设计来说，它让输出更稳定；对团队负责人来说，它让经验沉淀和治理有了抓手。所以 Skill 的核心收益不是多快，而是多稳、多可复用。

### P8｜不是所有流程都值得做成 Skill，先看频率、稳定性和可验证性

- 建议时长：4 分钟
- 页面目标：防止团队一上来就大规模造 Skill，制造噪音资产
- 版式建议：左边放“值得做”的三条件，右边放四个反例
- 页内内容：
  - 判断 1：是不是高频重复出现
  - 判断 2：步骤和边界是不是相对稳定
  - 判断 3：结果是不是容易验收
  - 反例 1：一次性任务也硬沉淀成 Skill
  - 反例 2：边界不清、人人理解不同的流程
  - 反例 3：明明该自动执行的守门逻辑却做成 Skill
- 讲稿：

> 这一页很关键，因为很多团队一兴奋就会开始堆 Skill，最后出现“看起来很多、其实没人用”的噪音资产。更稳的判断标准是三个：高频、稳定、可验证。高频意味着确实值得沉淀；稳定意味着它不会每次都换一套玩法；可验证意味着你能判断这个 Skill 有没有真的帮上忙。反过来说，一次性任务、边界模糊的流程、本该自动执行的风险拦截，都不适合直接做成 Skill。这个判断先做对，后面的制作才不会跑偏。

### P9｜第一个 Skill 不要做大，先把触发条件和输出形状写对

- 建议时长：4 分钟
- 页面目标：给出一个足够小、能落地的制作方法
- 版式建议：左边放最小骨架，右边放制作顺序
- 页内内容：
  - 第一步：写清什么时候该触发
  - 第二步：写清什么时候不该触发
  - 第三步：写清步骤顺序和输出格式
  - 第四步：写清限制条件，不让它越界
  - 结论：第一个版本先求稳，不求全

```markdown
---
name: fix-bug
description: 在用户描述 bug、报错、失败测试、异常回归时使用。先定位根因，再做最小修复，并补一个回归验证。
---

1. 先复述现象、影响范围和复现条件。
2. 搜索相关代码、日志和最近改动，确认根因。
3. 只做最小修复，不顺手重构无关部分。
4. 补一个最贴近故障面的验证。
5. 输出：根因、修改点、验证结果、剩余风险。
```

- 讲稿：

> 这一页是“怎么开始”的核心。第一个 Skill 千万不要做大而全，先做一个最小可用版本。最重要的不是正文写多长，而是先把四件事写清楚：什么时候该触发，什么时候不该触发，执行时按什么顺序走，最后输出长什么样。上面这个 `fix-bug` 骨架就够做第一轮测试了。很多人会把时间花在堆背景说明上，但真正决定 Skill 是否稳定的，往往是触发条件和输出形状，而不是文字总量。

### P10｜先有通用 Skill 本体，再做宿主适配

- 建议时长：3 分钟
- 页面目标：防止团队一上来就被某个工具的目录结构或入口绑死
- 版式建议：做三层结构图，底层是 `SKILL.md`，中间是 `scripts/` 和 `references/`，顶层是不同宿主入口
- 页内内容：
  - 第一层：通用 Skill 本体，通常是 `<skill-name>/SKILL.md`
  - 第二层：按需补 `scripts/`、`references/`、`assets/`
  - 第三层：再映射到 Claude、Codex 或其他宿主
  - 示例：Claude 常见是 `/skill-name`，Codex 常见是 `$skill-name`
  - 结论：宿主入口只是适配层，不是 Skill 的唯一真实形态
- 讲稿：

> 这一页要讲一个经常被忽略的方法论：先有通用 Skill 本体，再做宿主适配。也就是说，先把能力本身写清楚，再决定它在 Claude 里怎么触发，在 Codex 里怎么触发，在别的宿主里怎么接。这样做的好处是，团队维护的是同一份能力定义，而不是为每个工具各写一套。宿主入口只是适配层，不应该反过来定义 Skill 本体。这个顺序不对，后面一旦要迁移或共享，成本就会上来。

## 案例拆解：先讲内部落地，再用外部案例补结构感

### P11｜真正反复出错的不是“不会写”，而是“写得不像这个项目”

- 建议时长：4 分钟
- 页面目标：用 `docs-writing-style` 案例说明，为什么重复判断值得沉淀成 Skill
- 版式建议：左边放“没有 Skill 时的漂移”，右边放“有 Skill 后的固定动作”
- 页内内容：
  - 场景：文档站内容页更新频繁，页面类型很多
  - 问题：AI 容易把模块页、示例页、导读页混成一种写法
  - Skill 做的事：先读规则、先分页面类型、再决定写法
  - 关键价值：让“写得像这个仓库”从个人感觉变成可执行流程
  - 结论：很多重复问题不是语言能力问题，而是项目风格判断问题
- 讲稿：

> 这一页用仓库里的 `docs-writing-style` 做内部主案例。它最有代表性的地方在于，问题根本不是“模型不会写中文”，而是“模型不知道这个项目怎样才算写得像自己”。如果没有这类 Skill，AI 很容易把模块页、示例页、导读页混成一种模板，或者只看局部段落就动手改，最后把原本的教学节奏弄乱。这个 Skill 做的事情，不是替作者思考内容，而是先把必须做的判断顺序固定下来：先读仓库规则，再分页面类型，再看同类页面，再开始写。这个案例非常适合拿来说明，为什么重复出现的结构判断值得沉淀成 Skill。

### P12｜Skill 不该只让研发会用，也要让非研发能受益

- 建议时长：4 分钟
- 页面目标：用部门级共享案例说明 Skill 的组织价值和跨角色协作方式
- 版式建议：做一张三层参与模型图，分别是“消费结果 / 使用 Skill / 维护 Skill”
- 页内内容：
  - 消费结果：管理者、外部协作方
  - 使用 Skill：产品经理、设计师
  - 维护 Skill：研发、Tech Lead
  - 关键机制：反馈通道，让非研发经验也能沉淀回 Skill
  - 结论：非研发不必会写 Skill，但他们的经验必须能进入 Skill
- 讲稿：

> 这一页解决的是组织层问题。很多团队一说 Skill，默认就把它当成研发内部资产，但如果只有研发能用和能改，那团队能力只升级了一半。更稳的分层是三层：有些人只消费标准化结果，比如管理者；有些人通过熟悉的入口直接使用 Skill，比如产品或设计；还有一层是负责维护 Skill 的研发和 Tech Lead。关键不是要求所有人都学会写 `SKILL.md`，而是要有一条低门槛反馈通道，让非研发在真实工作中发现的问题，也能回写成 Skill 的更新。这一步一旦建立，Skill 才真正开始从个人工具变成部门资产。

### P13｜先用现成能力，再决定哪些问题值得自建

- 建议时长：4 分钟
- 页面目标：用官方 Skills 速查说明“现成能力”和“自建能力”的边界
- 版式建议：四张能力卡片加一条判断线。卡片建议用 `pdf`、`docx`、`pptx`、`skill-creator`
- 页内内容：
  - `pdf`：处理 PDF 的读取、拆分、合并和 OCR
  - `docx`：创建和编辑 Word 文档
  - `pptx`：生成和编辑演示文稿
  - `skill-creator`：帮助团队从零创建和迭代 Skill
  - 结论：先问“有没有现成能力”，再问“我们是否真的需要自建”
- 讲稿：

> 讲到这里，大家可能会有一个很现实的问题：是不是所有东西都要自己做？其实不是。官方 Skills 的价值就在这里，它提供了很多已经打磨过的现成能力，比如处理 PDF、Word、PPT，或者直接帮助团队创建和迭代新 Skill 的 `skill-creator`。这页要传达的判断很简单：先问有没有现成能力可以直接拿来用，再问哪些问题真的值得你们自己沉淀。自建 Skill 的价值在于项目约束、团队经验和专项流程；通用能力如果官方已经做得够好，优先复用通常更划算。

### P14｜gstack、superpowers、GSD 分别代表三种不同的进阶方向

- 建议时长：5 分钟
- 页面目标：给团队建立外部生态地图，但不把案例讲成安装指南
- 版式建议：三列比较表，分别标出“角色编排”“流程闭环”“上下文稳定”
- 页内内容：
  - gstack：更像角色化 Skill Pack，强调多视角显式编排
  - superpowers：更像默认工程流水线，强调设计先行、计划驱动、验证闭环
  - GSD：更像上下文工程层，强调规格、状态和阶段结论的持续稳定
  - 结论 1：三者不是谁更强，而是解决的问题不同
  - 结论 2：团队不要一上来就全套照搬，先借结构，再决定是否引入
- 讲稿：

> 这一页的目标不是带大家去装三套系统，而是建立一个判断框架。`gstack` 代表的是角色化编排思路，它把不同视角做成不同入口；`superpowers` 代表的是流程闭环思路，它更关注设计、计划、实现、验证能否自动串起来；`GSD` 代表的是上下文稳定思路，它解决的是长链路任务里的规格漂移和状态失真。对团队来说，这三者最值得借鉴的不是命令数量，而是结构价值。先判断你现在缺的是角色视角、流程纪律，还是长期上下文稳定，再决定要借哪一层。

## 落地与收尾：把讨论收束成团队下一步

### P15｜团队 30 天落地，不要先铺满，而要先跑通最小闭环

- 建议时长：5 分钟
- 页面目标：把方法论收束为一个可以执行的最小落地路径
- 版式建议：做四周时间线，从第 1 周到第 4 周
- 页内内容：
  - 第 1 周：选 1 个每周至少做两次的高频任务，写成第一个 Skill
  - 第 2 周：选 1 个真正能拦住风险的动作，做成 Hook 草稿
  - 第 3 周：建立 1 条低门槛反馈通道，收集团队真实问题
  - 第 4 周：回看调用频率、输出稳定性和维护成本，决定保留或迭代
  - 结论：先做 1 个 Skill + 1 个 Hook + 1 条反馈通道，比先造 10 个命令更稳
- 讲稿：

> 这一页是全场最重要的落地页，因为如果最后只停在概念介绍，这场分享的价值会很有限。我建议团队的最小路径不是一上来铺很多 Skill，而是先跑通一个小闭环。第一周，挑一个每周至少做两次、边界也清楚的任务，做成第一个 Skill；第二周，再挑一个你们最不想靠人工记忆的风险动作，写成 Hook 草稿；第三周，建立一条反馈通道，让真实使用者可以提交问题；第四周，再一起复盘它有没有真的减少重复解释、有没有更稳定、维护成本是否能接受。这个节奏很小，但很稳。

### P16｜真正要带走的不是更多命令，而是更稳定的协作方式

- 建议时长：2 分钟
- 页面目标：收束全场，给出 3 条 takeaway，并引导 Q&A
- 版式建议：浅色收尾页，左边三条 takeaway，右边放 Q&A 提问引导
- 页内内容：
  - Takeaway 1：Skill 解决的是“怎样稳定地做一类事”
  - Takeaway 2：先做高频、稳定、可验证的那一小批
  - Takeaway 3：先有 Skill 本体，再做宿主适配和组织共享
  - Q&A 提示：你所在团队现在最值得先做成 Skill 的一件事是什么
- 讲稿：

> 最后一页，我希望大家带走三件事。第一，Skill 不是更长的 prompt，而是让一类工作稳定发生的入口。第二，不是所有流程都值得做成 Skill，先抓高频、稳定、可验证的那一小批。第三，真正有价值的 Skill，不是写出来就结束，而是能继续接反馈、能跨角色共享、能逐步长成团队能力。如果今天这场分享结束后，大家能开始讨论“我们团队现在最值得先做成 Skill 的一件事是什么”，那这场分享就已经达到目标了。下面我们进入 Q&A。

## 用这份讲稿时的三个提醒

- 不要把分享讲成工具盘点。主线一定是“为什么要做、如何判断、怎样开始、如何落地”。
- 不要把外部案例讲成默认方案。`gstack`、`superpowers`、`GSD` 的作用是帮助团队建立结构感，不是要求直接照搬。
- 不要在一场混合团队分享里塞太多安装细节。命令、目录、宿主差异只讲到足够说明问题即可。
