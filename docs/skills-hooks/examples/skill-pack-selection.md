# 工作流选型：gstack、superpowers 和 GSD 怎么看

> **定位：** 这一页不是官方 Skill 列表，也不是单案例拆解页。它只解决一个问题：当你已经知道要看外部工作流体系时，`gstack`、`superpowers` 和 `GSD` 分别该在什么情况下看、借什么、避开什么。

---

## 先判断你要找的是什么

- 如果你要的是**官方现成能力**，先看 [Anthropic 官方 Skills 速查](./official-skills-catalog)
- 如果你要的是**自己做第一个 Skill**，先看 [如何制作 Skills](../advanced-patterns)
- 如果你要的是**外部工作流体系选型**，再继续读这一页

这一步很重要，因为很多读者其实不是在选 `gstack` / `superpowers` / `GSD`，而是在找“有没有现成 Skill 可以直接用”。这两类需求不该混在一起。

---

## 先看结论

- 如果你想显式调用不同专家角色，让 AI 在 CEO、设计、评审、QA、安全、发布之间切换，优先看 **gstack**
- 如果你想把设计、计划、实现、测试、审查做成一条默认自动推进的工程流水线，优先看 **superpowers**
- 如果你的项目会跨很多会话、阶段长、容易在规格和状态上漂移，再把 **GSD** 作为补充的"上下文稳定层"引入，而不是一开始就把它当第三套主工作流
- 如果团队已经有自己的主工作流，不建议同时把两者都作为默认主编排层启用

---

## 核心区别

| 维度 | gstack | superpowers | GSD |
|------|--------|-------------|-----|
| **核心定位** | 角色化 Skill Pack，把 Agent 变成"虚拟工程团队" | 方法论驱动的工作流插件，把 Agent 变成"默认遵守流程的交付系统" | 上下文 / 规格稳定层，把项目状态、决策和阶段性结论固定下来 |
| **解决的主要问题** | 需求和方案需要多角色视角审视 | 需求清楚后，怎样稳定推进设计、计划、实现和验证 | 项目做久了以后，怎样避免规格、状态和决策漂移 |
| **工作方式 / 触发方式** | 以 `/office-hours`、`/review`、`/qa`、`/ship` 这类显式命令为主 | 相关 Skill 自动触发，用户通常不需要手动点名 | 通过持续沉淀需求、决策、状态文档来稳住后续会话 |
| **最适合的场景** | 需要显式调度不同视角、人工编排较多的团队 | 需要默认工程纪律、尽量少漏步骤的团队 | 长周期、多阶段、频繁中断恢复的项目 |
| **典型代价 / 不适合场景** | 角色和命令较多，短任务里会显得偏重 | 流程约束较强，不适合高度手动编排 | 单独使用时不直接替你完成交付，短任务里可能多一层维护负担 |

可以把三者简单理解成：`gstack` 偏角色视角与决策，`superpowers` 偏执行闭环，`GSD` 偏规格、状态和上下文稳定。对大多数团队来说，前两者是在选主工作流，`GSD` 只在长期上下文漂移已经成为真实问题时再补进来。

---

## 读这些案例时，重点看什么

不要把这三页当成“直接照装哪一套”的安装教程，更稳的看法是：

- 看它解决的主要问题，是不是你现在真实存在的瓶颈
- 看它默认要求的协作习惯，你的团队能不能接受
- 看它最值得借鉴的结构，是否能只吸收一部分而不是全盘照搬
- 看它最大的代价和冲突点，避免只是因为“看起来完整”就引入

这一组案例页更适合做“结构判断样本”，而不是“默认推荐方案清单”。

---

## 什么时候更适合选 gstack

- 你希望显式调用不同角色，比如先做 CEO 视角评审，再做 QA，再做安全审查
- 你想保留较高的人工编排权，而不是把流程自动化到底
- 你需要更完整的角色覆盖，例如设计评审、发布、灰度、安全、复盘
- 你更关心"多视角审查是否充分"，而不是"流水线是否自动推进"

---

## 什么时候更适合选 superpowers

- 你更在意"默认不乱来"，希望 Agent 先设计、再计划、再实现
- 你想把 TDD、review、完成前验证做成流程内置约束
- 你希望 Agent 能沿着计划连续自主工作较长时间，而不是频繁等你发 `/command`
- 你更关心"流程是否稳定收敛"，而不是"是否有很多可手动调用的专家角色"

---

## 不建议直接混用的情况

两者都属于强约束体系。

如果在同一会话里同时把它们当作默认工作流启用，常见问题会是：

- 流程触发点重叠，Agent 不知道该优先遵循哪套方法
- 角色化命令和自动化流水线都在争夺主编排权
- 用户以为自己在"叠加能力"，实际是在制造冲突和重复约束

更稳的做法是：

- 选一套做**主编排层**
- 另一套只把少量设计思想吸收到自己的规则、Skill 或团队规范里

对大多数团队来说，先在 `gstack` 和 `superpowers` 之间定一个主工作流已经足够。只有当项目明显跨会话、跨阶段，并且开始出现上下文漂移时，再考虑补 `GSD`。技术方案越多，心智负担越重，文档和流程都应该优先帮团队减负。
