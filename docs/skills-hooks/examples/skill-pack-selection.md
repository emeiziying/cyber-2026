# Skill Pack 选型：gstack 和 superpowers 怎么选

> **定位：** 这一页只解决选型问题。`gstack` 和 `superpowers` 各自是什么、怎么工作，放在各自案例页里展开；这里重点回答它们分别适合什么团队、什么协作习惯。

---

## 先看结论

- 如果你想显式调用不同专家角色，让 AI 在 CEO、设计、评审、QA、安全、发布之间切换，优先看 **gstack**
- 如果你想把设计、计划、实现、测试、审查做成一条默认自动推进的工程流水线，优先看 **superpowers**
- 如果团队已经有自己的主工作流，不建议同时把两者都作为默认主编排层启用

---

## 核心区别

| 维度 | gstack | superpowers |
|------|--------|-------------|
| **核心定位** | 角色化 Skill Pack，把 Agent 变成"虚拟工程团队" | 方法论驱动的工作流插件，把 Agent 变成"默认遵守流程的交付系统" |
| **触发方式** | 以 `/office-hours`、`/review`、`/qa`、`/ship` 这类显式命令为主 | 相关 Skill 自动触发，用户通常不需要手动点名 |
| **主隐喻** | 召唤 CEO、设计师、Reviewer、QA、安全官等不同角色 | 让 Agent 严格走 brainstorming → plans → subagents → TDD → review 的流水线 |
| **用户控制方式** | 用户自己决定现在该调用哪个角色、走到哪一步 | 用户更像批准设计和计划，之后由系统推进下一步 |
| **工作流重心** | 多角色、多视角评审，以及 QA / 安全 / 发布等完整职能覆盖 | 设计先行、任务细化、工作树隔离、TDD 和自动化执行 |
| **最适合的团队习惯** | 喜欢显式调度专家角色、按阶段手动推进 | 喜欢把工程纪律做成默认行为、尽量少漏步骤 |

可以把两者简单理解成：

- **gstack**：专家角色工具箱
- **superpowers**：默认执行的开发流水线

---

## 什么时候更适合选 gstack

- 你希望显式调用不同角色，比如先做 CEO 视角评审，再做 QA，再做安全审查
- 你想保留较高的人工编排权，而不是把流程自动化到底
- 你需要更完整的角色覆盖，例如设计评审、发布、灰度、安全、复盘
- 你更关心"多视角审查是否充分"，而不是"流水线是否自动推进"

---

## 什么时候更适合选 superpowers

- 你更在意"默认不乱来"，希望 Agent 先设计、再计划、再实现
- 你想把 TDD、review、完成前验证做成流程内置约束
- 你希望 Agent 能沿着计划连续自主工作较长时间，而不是频繁等你发 `/command`
- 你更关心"流程是否稳定收敛"，而不是"是否有很多可手动调用的专家角色"

---

## 不建议直接混用的情况

两者都属于强约束体系。

如果在同一会话里同时把它们当作默认工作流启用，常见问题会是：

- 流程触发点重叠，Agent 不知道该优先遵循哪套方法
- 角色化命令和自动化流水线都在争夺主编排权
- 用户以为自己在"叠加能力"，实际是在制造冲突和重复约束

更稳的做法是：

- 选一套做**主编排层**
- 另一套只把少量设计思想吸收到自己的规则、Skill 或团队规范里
