# 用 docs-writing-style 理解为什么项目要定义 Skill

## 背景 / 问题

`Cyber 2026` 不是一个只有几页说明文的仓库，而是一套有明确教学路径的文档站。
这里既有模块主文档，也有侧边栏中的独立教学页，还有大量示例页；与此同时，[开始阅读](../../intro/) 这样的导读页和首页又是另一种写法。

如果没有一套专门面向“内容页写作”的稳定工作流，AI 在帮仓库补文档时很容易出现几类漂移：

- 把模块页、示例页、导读页混成一种模板
- 忘记模块页里已经稳定存在的收尾结构
- 只看单个段落就动手修改，破坏原本的教学节奏
- 把某一页里偶然出现的写法误当成全站默认规则

这类问题的共同点是：它们不是“模型不会写中文”，而是“模型不知道这个仓库怎样才算写得像自己”。

这也是为什么 [Skills & Hooks](../) 这一章强调，很多重复问题不能只靠临场 prompt 解决，而要沉淀成可复用能力。

---

## docs-writing-style 在这个项目里做什么

`docs-writing-style` 做的不是代替作者思考内容，而是把“在这个仓库里写内容页时必须先做的判断和准备动作”固定下来。

它至少解决了四件事。

### 先限定适用范围

这个 Skill 并不把所有 `docs/` 文件都当成同一种对象处理。
它明确只面向内容页，例如：

- `docs/**/index.md` 里的模块页
- 像 `docs/skills-hooks/advanced-patterns.md` 这样的侧边栏教学页
- `docs/**/examples/*.md` 下的案例页

同时，它也明确排除了首页、导读页和仓库级说明文件，避免把不该套模板的页面硬改成“标准章节页”。

### 先判断页面类型，再决定写法

这个仓库里，模块页和示例页的写法并不一样。

- 模块页通常有 `适合人群 / 学习目标`，并带有稳定的章节收尾结构
- 示例页更强调背景、过程、判断和经验沉淀，不应该被写成统一编号的小课程

`docs-writing-style` 的价值，就在于先帮 AI 做这层分类，而不是拿到任意页面就直接生成。

### 先读规则和同类页面，再开始写

这个 Skill 要求在动手前先读 `AGENTS.md`，再读目标页和同类页面。
这一步很重要，因为它把“按仓库事实写作”变成了默认动作，而不是碰运气。

在这个项目里，这意味着 AI 不只是知道“要写中文、链接不带 `.md`、只用 H2/H3”，还会去对照同类页面，理解哪些结构是稳定模式，哪些只是单页特性。

### 保留仓库已经存在的节奏，而不是强行统一

`docs-writing-style` 不是新的设计系统，它更像一个“防漂移层”。
它要求保留已有页面里有教学价值的结构差异，例如：

- 模块页沿用已经稳定的教学骨架
- 独立教学页保留自己的收尾方式
- 示例页保持案例叙述感，不被改写成僵硬模板

换句话说，它不是让每一页都长得一样，而是让每一类页面都更像它本来应该有的样子。

## 为什么这件事要定义成 Skill，而不是每次临时写 prompt

如果只是偶尔改一页文档，临时 prompt 当然也能工作。
但这个仓库的内容页更新是高频动作，而且页面类型清晰、质量标准稳定、好坏也容易判断，这正是适合沉淀成 Skill 的典型场景。

把它定义成 Skill，有几个直接好处。

### 减少重复解释

每次都重新告诉 AI：

- 先看 `AGENTS.md`
- 先判断页面类型
- 模块页和示例页不要混写
- 不要把首页写法带进内容页

这些说明本身就是重复劳动。写进 Skill 之后，这部分不必在每次会话里从头再说一遍。

### 减少风格漂移

临时 prompt 很容易受上下文影响。
这次强调了结构，下次又只强调语气，再下次换了协作者，约束就开始丢失。

Skill 的价值在于把一组稳定、长期有效的工作方法固定下来，让不同人、不同会话、不同 agent 在处理同类任务时，默认站在同一条起跑线上。

### 让经验从个人习惯变成团队资产

“写得像这个仓库”通常一开始只存在于少数维护者的感觉里。
如果不把它写成 Skill，这种经验就只能存在于聊天记录、口头提醒和 review 评论中。

一旦定义成 Skill，它就从个人习惯变成了团队可复用资产，后续维护者和新加入的协作者都能直接继承。

### 降低协作门槛

一个好的 Skill，不只是给创建它的人自己用。
它还能让后来接手的人不必先完整理解整个仓库的历史，也能按照已有方法稳定补页、改页、扩展示例。

这和 [如何制作 Skills](../advanced-patterns) 里讲的思路一致：先把高频、稳定、可验证的工作流做成通用源文件，再按需要接到具体任务里。

## 它和 AGENTS.md 是什么关系

这两者不是替代关系，而是分工关系。

`AGENTS.md` 负责定义这个仓库的项目级硬约束，例如：

- 站点是什么、目录怎么组织
- 文档语言、标题层级、链接写法
- 新增模块或示例页时，哪些导航位置必须同步
- 哪些行为明确禁止

这些规则面向整个仓库，不只服务于某一类写作任务。

`docs-writing-style` 则更像一份“内容页写作 SOP”：

- 它只服务于 `docs/` 下特定类型的内容页
- 它关心的是这类任务该先读什么、先判断什么、如何避免套错模板
- 它把仓库里已经稳定存在的页面节奏整理成可执行流程

更准确地说，`AGENTS.md` 定义边界，Skill 负责执行。

这也是为什么 `docs-writing-style` 自己会明确优先级：
先遵守用户当前要求，再遵守 `AGENTS.md`，然后看页面本身和仓库事实，最后才用 Skill 里的通用形状做兜底。

如果少了 `AGENTS.md`，Skill 就容易失去项目事实依据；
如果少了 Skill，`AGENTS.md` 里的约束又很难在具体写作任务里被稳定执行。

## 这个案例能带来的启发

`docs-writing-style` 之所以是一个合适的 Skill，不是因为“文档写作很重要”，而是因为它符合几条更通用的判断标准：

- 这是一类会反复出现的任务
- 任务边界清楚，不适用范围也能说清楚
- 执行前需要固定的判断顺序
- 输出质量可以根据仓库事实直接检查

当一项工作同时满足这几个条件时，就值得从“临时 prompt”升级成 Skill。

如果你在项目里也遇到类似情况，可以反过来问自己：

- 这类要求是不是几乎每次都要重复说？
- 它是不是已经有比较稳定的输入、步骤和验收标准？
- 它的经验是不是只掌握在少数人手里？

如果答案大多是“是”，那它通常就不该继续停留在聊天技巧层面，而应该被沉淀成 Skill。

至于什么时候该做 Hook，而不是 Skill，可以继续看 [Skill 与 Hook 判断案例](./skill-hook-decision-cases)；如果你已经确认值得做 Skill，再回到 [Skills & Hooks](../) 主章或 [如何制作 Skills](../advanced-patterns) 继续往下走。
