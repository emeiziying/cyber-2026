# 如何使用Skills实现赛博飞升

这是一份面向跨职能团队的分享讲稿底稿，按 45-50 分钟设计，可直接拆成 PPT。  
每一页都分成四部分：`页标题`、`屏幕文案`、`讲述要点`、`可视化建议`。屏幕文案用于投影，讲述要点用于口播展开。

---

## 使用方式

- 适合第一次向团队系统介绍 Skills 的场景
- 适合研发、产品、设计、管理者共同在场的分享
- 适合先讲认知，再讲做法，最后讲试点落地

如果你需要先补概念背景，可以先读 [开始阅读](../../intro/)；如果你要把这套分享继续拆成专题课，可以配合 [Skills & Hooks](../)、[如何制作 Skills](../advanced-patterns) 和 [部门级 Skill 共享](./dept-skill-sharing) 一起使用。

## 第一部分：开场与认知

### 第 1 页：封面

**页标题：** 如何使用Skills实现赛博飞升

**屏幕文案：**

- 如何使用Skills实现赛博飞升
- 演讲人：`姓名 / 团队`
- 日期：`分享日期`

**讲述要点：**

- 封面不要承担信息密度，只负责建立主题和身份信息。
- 如果需要补场景说明，可以在口播里一句带过：“这是一场面向跨职能团队的 AI 工作流分享。”
- 真正的内容密度从下一页开始，封面尽量留白，避免一上来就堆概念。

**可视化建议：**

- 封面优先纯文字排版，只保留标题、演讲人、日期
- 如果要放图，只作为角落弱化装饰，不要占据主视觉中心
- 版式建议大标题居中或偏左，演讲人和日期放底部小字

### 第 2 页：破题

**页标题：** 今天不只是讲几个好用命令

**屏幕文案：**

- 个人会用 AI，不等于团队会交付
- 一次性 prompt，不等于稳定工作流
- 零散技巧，不等于共享能力

**讲述要点：**

- 很多团队已经在用 AI，但常见状态是每个人各自摸索，各自问得很快，最后组织层面却没有形成共同方法。
- 如果一套好做法只能存在于聊天记录里，它就仍然是个人技巧，不是团队能力。
- 今天这套分享的目标，是把“会问”升级成“会沉淀、会复用、会共享”。

**可视化建议：**

- 左右对照：左边是个人聊天窗口，右边是团队共享流程图
- 三个短句用红绿对比，突出“不是 / 而是”

### 第 3 页：什么是赛博飞升

**页标题：** 赛博飞升有两层含义

**屏幕文案：**

- 第一层：团队 AI 能力升级
- 第二层：经验沉淀成数字资产
- 重点不是更会写 prompt，而是更会构建能力

**讲述要点：**

- 第一层讲的是能力升级：团队不再只停留在“偶尔问一问 AI”，而是逐步具备认知转变、协作方式和工具判断的能力。
- 第二层讲的是资产化：稳定的判断、约束和流程，不应该只留在个人脑子里，而应该沉淀成可复用的数字资产。
- 对应到这套方法论里，反复出现的约束会写成 rule，稳定流程会封装成 Skill 或自动化，更复杂的高价值能力才会继续升级成 Agent。

**可视化建议：**

- 做成“两层台阶”图：能力升级在上，资产沉淀在下
- 右侧放三个小标签：rule / Skill / Agent

### 第 4 页：为什么赛博飞升不能只靠 prompt

**页标题：** 会问，不等于会交付

**屏幕文案：**

- prompt 解决一次对话
- 交付需要边界、流程和验收
- 团队能力依赖共享，而不是个人发挥

**讲述要点：**

- prompt 当然重要，但它更像一次性输入方式，解决的是“这次怎么问”。
- 真正影响交付稳定性的，是边界有没有写清楚、流程有没有固定下来、验收有没有形成默认标准。
- 所以赛博飞升不是“把 prompt 写得越来越花”，而是把重复经验逐步沉淀到更稳定的层里。

**可视化建议：**

- 漏斗图：prompt 在上层，下面依次流向流程、验收、共享
- 屏幕上可用一句强调语：个人效率不自动等于团队能力

### 第 5 页：方法论地图

**页标题：** Skills 在整套方法论里的位置

**屏幕文案：**

- prompt：一次性表达
- rule / MCP / Skill / Agent：分层构建能力
- 治理：把能力接进团队协作

**讲述要点：**

- 这一页要帮听众建立坐标系，不然后面很容易把 Skill 当成万能容器。
- prompt 解决单次表达；rule 负责边界和约束；MCP 负责接外部工具；Skill 负责可复用工作流；Agent 负责更重的连续执行；治理负责把这些层接入团队运行。
- Skills 很关键，但它只是中间层。理解它的位置，才能知道什么时候该用，什么时候不该用。

**可视化建议：**

- 用分层阶梯图或能力栈图表示六层关系
- 给 Skills 这一层加高亮，强调它是今天的主角

### 第 6 页：为什么 Skills 是关键抓手

**页标题：** Skills 是从“会用”到“可重复”的过渡层

**屏幕文案：**

- 它在认知完成后、Agent 之前
- 它最适合承接高频工作流
- 它最容易先做出团队收益

**讲述要点：**

- 很多团队一上来就想做 Agent，但实际上更常见的高价值动作，是先把高频、稳定、容易验证的流程做成 Skills。
- Skill 的门槛比 Agent 低，但比一次性 prompt 稳定得多，所以特别适合作为团队第一批 AI 资产。
- 如果要快速看到赛博飞升的组织收益，Skills 往往比直接做复杂 Agent 更现实。

**可视化建议：**

- 用一条成长路径表示：prompt → Skill → Agent
- 在 Skill 位置标注“最适合第一批沉淀”

## 第二部分：Skills 的概念与边界

### 第 7 页：Skills 解决什么问题

**页标题：** 团队已经开始用 AI 后，会出现新的重复劳动

**屏幕文案：**

- 同一种 bug 修复说明反复说
- 同一种 review 格式反复要求
- 同一种上下文反复补
- 同一种输出结构反复重建

**讲述要点：**

- 当团队还没有稳定使用 AI 时，痛点是“不会用”；一旦开始稳定使用，新的痛点就会变成“重复说同样的话”。
- 这类问题不一定复杂，但非常消耗注意力，而且最容易因为换人、换会话、换上下文而漂移。
- Skills 的价值，就是把这些高频重复动作封装成可复用、可共享、可维护的入口。

**可视化建议：**

- 用四个重复回环图标，对应 bug、review、context、output
- 背景可以用“聊天记录不断重复滚动”的视觉隐喻

### 第 8 页：Skill 是什么

**页标题：** Skill 是“主动发起的可复用工作流入口”

**屏幕文案：**

- 由用户主动触发
- 面向一类稳定任务
- 带步骤、边界和输出格式

**讲述要点：**

- Skill 不是一句 magic prompt，而是一类稳定任务的入口。
- 它适合用户主动发起的复杂流程，例如修 bug、做 code review、生成测试、整理文档、产出日报。
- 一个好的 Skill 不只是写“做什么”，还会把步骤顺序、输出结构和限制条件一起固定下来。

**可视化建议：**

- 用“按钮 / 入口”图形表示 Skill 的触发感
- 旁边放三张卡片：步骤、边界、输出

### 第 9 页：Skill 不是什么

**页标题：** Skill 不是所有事都该塞进去的总容器

**屏幕文案：**

- 不是一次性 prompt
- 不是自动守门的 Hook
- 不是职责更重的 Agent

**讲述要点：**

- 一次性 prompt 解决的是临时表达，不一定值得长期维护成 Skill。
- Hook 更像事件触发的自动守门逻辑，例如自动补环境信息、危险命令拦截、调用后审计记录。
- Agent 适合更复杂的连续执行和状态判断。如果一个任务本来只需要固定工作流，就没必要硬升级成 Agent。

**可视化建议：**

- 做三栏对照：prompt / Hook / Agent / Skill
- 让 Skill 居中，强调它和两侧边界的区别

### 第 10 页：怎么判断值不值得做成 Skill

**页标题：** 先看四个信号

**屏幕文案：**

- 高频
- 稳定
- 可验证
- 边界清楚

**讲述要点：**

- 高频，代表它值得投入维护成本；稳定，代表它不会每周都变；可验证，代表大家能判断它到底有没有帮到忙；边界清楚，代表团队知道什么时候该调它。
- 如果一个流程很少出现、适用范围说不清、输出也不好验，那通常不该急着做成 Skill。
- 团队做第一批 Skill 时，宁可少，也不要做成“大而全技能市场”。

**可视化建议：**

- 用四象限或四个判断灯显示这四个信号
- 可加一句注释：满足越多，越适合先沉淀

### 第 11 页：一个 Skill 的最小形态

**页标题：** 先做 Skill 本体，再做宿主适配

**屏幕文案：**

- `SKILL.md` 是本体
- `scripts/`、`references/`、`assets/` 按需添加
- 宿主接入是第二层，不是第一层

**讲述要点：**

- 更稳的默认做法，是先把 Skill 写成宿主无关的源文件，而不是一开始就绑定某个工具专属目录。
- 第一版只要 `SKILL.md` 足够清楚，已经可以开始验证；只有在需要确定性脚本、参考资料或资源模板时，再拆到其他目录。
- 这样做的好处是，未来无论接到 Claude、Codex 还是其他宿主，维护的都是同一份能力本体。

**可视化建议：**

- 用文件树示意：`SKILL.md` 居中，其他目录作为可选分支
- 把“宿主适配”画成外圈，而不是核心

## 第三部分：案例与组织化

### 第 12 页：案例一

**页标题：** 为什么有些经验不能只留在聊天记录里

**屏幕文案：**

- `docs-writing-style` 解决的是内容页漂移
- 它先判断页面类型，再决定写法
- 它把少数维护者经验变成团队资产

**讲述要点：**

- 这个案例很适合解释 Skill 的真实价值，因为问题不在于“模型不会写中文”，而在于“模型不知道这个仓库怎样才算写得像自己”。
- `docs-writing-style` 固定了几件事：先读项目规则、先判断页面类型、先对照同类页面、再开始写。
- 一旦这些经验写进 Skill，它就不再只是少数维护者的口头感觉，而变成可复用的团队 SOP。

**可视化建议：**

- 左右对照：无 Skill 时的页面漂移 vs 有 Skill 时的稳定产出
- 可以放“先判断，再动手”的流程箭头

### 第 13 页：案例二

**页标题：** 先借现成能力，再决定自建什么

**屏幕文案：**

- 官方已有一批常见 Skills
- 自建不等于从零发明一切
- 关键是看团队缺的是什么

**讲述要点：**

- 官方生态里已经有 `pdf`、`docx`、`pptx`、`xlsx`、`webapp-testing`、`skill-creator` 等一批现成能力。
- 这说明团队不必把“赛博飞升”理解成“所有东西都自己造”；更现实的顺序是先借现成能力，再针对自己的高频问题补齐自建 Skill。
- 判断标准不是“哪个更酷”，而是“哪些能力已经成熟可直接用，哪些痛点只有我们自己最清楚”。

**可视化建议：**

- 用“借力 + 自建”双轮模型
- 可以列 4-6 个代表性官方 Skill 作为示意，不铺满整页

### 第 14 页：案例三

**页标题：** 赛博飞升不能只让研发飞升

**屏幕文案：**

- 研发创建 Skill，不代表只有研发受益
- 非研发也需要可用入口
- 非研发经验也必须能反馈回 Skill

**讲述要点：**

- 如果只有研发能用和改 Skill，那只是技术侧在升级，业务侧还停留在原地。
- 真正的跨职能落地，要同时解决三件事：非研发怎么用、怎么消费标准化产出、怎么把他们的经验反馈回 Skill。
- 所以 Skill 共享不是“把一个目录丢给全员”，而是要设计角色分层和反馈闭环。

**可视化建议：**

- 用多角色人物图标表示研发、产品、设计、管理者
- 中间放一个 Skill 源仓，左右连“使用”和“反馈”

### 第 15 页：跨角色参与模型

**页标题：** 用三层参与方式组织跨职能协作

**屏幕文案：**

- 消费结果
- 使用 Skill
- 维护 Skill

**讲述要点：**

- 管理者和外部协作方不一定要直接触发 Skill，但可以消费 Skill 带来的标准化产出。
- 产品经理、设计师这类角色更适合通过自己熟悉的界面使用 Skill，而不需要直接维护源文件。
- 研发和 Tech Lead 通常负责维护 Skill 本体、审核反馈、决定哪些经验值得正式沉淀。

**可视化建议：**

- 三层金字塔或三层阶梯图
- 每层下方用小字标注典型角色

### 第 16 页：组织化落地方式

**页标题：** Skill 要变成共享能力，需要闭环

**屏幕文案：**

- 通用源仓
- 宿主映射
- 反馈模板
- Tech Lead 审核

**讲述要点：**

- 更稳的做法不是把某个宿主目录当唯一真相，而是维护一份通用 Skill 源仓，再按不同入口做映射。
- 同时要给非研发准备低门槛反馈模板，让他们知道“哪里不对”和“应该怎样”可以如何提交。
- 最后需要有人负责审核和转化，否则 Skill 很快就会变成没人维护的静态文件。

**可视化建议：**

- 画成闭环：源仓 → 宿主入口 → 使用反馈 → 审核更新 → 回到源仓
- 用单独颜色高亮“反馈模板”

![反馈闭环配图：匿名反馈](/skills-sharing/anonymous-feedback.svg)

### 第 17 页：外部工作流怎么看

**页标题：** 不同 Skill Pack，解决的是不同问题

**屏幕文案：**

- gstack：角色化视角
- superpowers：流程化执行
- GSD：上下文稳定层

**讲述要点：**

- 这一页不是安装教程，而是告诉听众：外部工作流体系的差别，不在命令多少，而在它们默认帮你解决哪类问题。
- gstack 更偏多角色视角与显式调度，superpowers 更偏工程流程闭环，GSD 更偏长期上下文和规格稳定。
- 对大多数团队来说，先看结构借鉴价值，比一上来全盘照搬更重要。

**可视化建议：**

- 三列表格，对比定位、优势、代价
- 每列只保留一句话标签，避免信息过载

## 第四部分：落地与行动

### 第 18 页：常见反模式

**页标题：** Skill 很容易做多，却不一定做对

**屏幕文案：**

- Skill 过多
- 大而全总 Skill
- Hook 乱做业务判断
- 没人维护

**讲述要点：**

- 第一类反模式是“越多越专业”，结果变成一堆没有人记得什么时候用的噪音资产。
- 第二类是把所有任务都塞进一个总 Skill，导致边界不清、维护困难、触发混乱。
- 第三类是 Hook 过度承担业务判断，第四类则是缺少明确维护责任人，这两类都会让自动化失控或失效。

**可视化建议：**

- 用四张“踩坑卡片”展示典型症状
- 可加一条底部警示语：能力多，不等于能力体系成熟

### 第 19 页：最小试点方案

**页标题：** 第一轮落地，不要从十个 Skill 开始

**屏幕文案：**

- 第 1 周：整理 3 个高频 Skill
- 第 2 周：接入 1 个非研发入口
- 第 3 周：建立反馈模板
- 第 4 周：复盘并更新源仓

**讲述要点：**

- 这条路径的重点不是追求完整，而是尽快验证“这套方式到底能不能减少重复劳动、提高产出稳定性”。
- 第一轮建议从最常见的三类场景入手，例如 bug 修复、review、文档整理。
- 只要跑通一个非研发入口和一个反馈闭环，团队就已经从“个人技巧”迈向“组织化能力”了。

**可视化建议：**

- 用四周时间轴表示推进节奏
- 每一周配一个明确产出物图标

### 第 20 页：收尾

**页标题：** 使用 Skills 实现赛博飞升，本质上是在做能力沉淀

**屏幕文案：**

- 不是堆更多名词
- 不是堆更多命令
- 而是把重复经验变成共享能力

**讲述要点：**

- 这一页要把标题再收回来，避免听众把分享理解成“Skill 功能介绍会”。
- 真正的重点不是学会多少术语，而是理解：为什么团队要把稳定经验从个人脑中迁移到可复用资产里。
- Skills 之所以关键，不是因为它最酷，而是因为它是最适合承接这类沉淀工作的那一层。

**可视化建议：**

- 用一句大字强调“重复经验 → 共享能力”
- 背景可回收第一页的流程图，形成首尾呼应

### 第 21 页：行动清单

**页标题：** 分享结束后，团队至少带走三件事

**屏幕文案：**

- 找出 1 个适合沉淀成 Skill 的流程
- 找出 1 个不该再靠记忆的提醒
- 选出 1 个最适合试点的角色

**讲述要点：**

- 第一件事，是从真实工作里找一个高频、稳定、可验证的流程，而不是空想一个“未来会有用”的 Skill。
- 第二件事，是识别一个必须自动守住的风险点，避免把所有问题都往 Skill 上推。
- 第三件事，是选一个最容易试点成功的角色或场景，让团队先看到收益，再谈扩展。

**可视化建议：**

- 用勾选清单展示三件事
- 每一项后面留一个空白占位，方便现场互动或会后填写

### 第 22 页：Q&A / 备用页

**页标题：** 常见追问与延伸阅读

**屏幕文案：**

- 什么适合 Skill，什么适合 Hook
- 什么时候该升级成 Agent
- 团队从哪里开始最稳

**讲述要点：**

- 如果现场有人想继续追问判断边界，可以回到 [Skill 与 Hook 判断案例](./skill-hook-decision-cases)。
- 如果有人想立刻开始做第一个 Skill，可以接 [如何制作 Skills](../advanced-patterns)。
- 如果有人更关心跨角色共享和维护方式，可以接 [部门级 Skill 共享](./dept-skill-sharing)、[工作流选型](./skill-pack-selection) 和 [官方 Skills 速查](./official-skills-catalog)。
