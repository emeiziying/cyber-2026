# 从设计稿到真实运行：UI 交付验收闭环

## 背景

团队要根据设计稿调整一个已有页面。AI 已经修改了组件和样式，类型检查、单元测试也都通过，但实际打开页面后仍可能出现这些问题：

- 页面级样式改对了，应用壳的默认背景仍然覆盖结果
- 桌面端接近设计稿，移动端出现遮挡或横向滚动
- 执行中的状态节点结束后被移除，导致页面上下跳动
- 浏览器预览正常，App 安装包中的原生能力却没有生效

这类任务不能把“代码已经修改”当成完成。更稳妥的交付方式，是把设计事实、实现位置和真实运行验收串成一条证据链。

---

## 先确定每个问题的事实来源

不同问题依赖不同证据，不能用一份截图或一段代码回答所有问题。

| 要回答的问题 | 优先事实来源 | 不能替代它的材料 |
|------|------|------|
| 页面应该长什么样 | 已确认的设计稿、交互说明、`DESIGN.md` | AI 根据截图做的自由推断 |
| 页面现在长什么样 | 指定路由、视口和数据状态下的真实运行页面 | 组件源码、构建成功日志 |
| 差异属于哪里 | 页面、共享组件、应用壳和主题配置的实际调用链 | 只看出现问题的页面文件 |
| App 原生能力是否生效 | 对应安装包和目标设备上的真实操作 | H5 预览、代码中存在配置项 |

设计稿描述目标，运行界面证明现状，代码负责解释差异。三者不能相互代替。

---

## 第一步：把验收对象说清楚

开始实现前，先记录一组可复现的验收条件：

| 要素 | 示例 |
|------|------|
| 页面或路由 | 巡检任务管理页 |
| 目标平台 | 桌面浏览器、移动浏览器、App |
| 视口 | 桌面端 1440px、移动端 390px |
| 数据状态 | 空状态、正常数据、加载中、部分失败 |
| 设计依据 | 已确认的设计稿与 `DESIGN.md` |
| 不包含项 | 不改接口、不重做应用壳、不扩展业务流程 |

如果没有固定路由、视口和数据状态，两张截图之间的差异很可能只是环境不同，无法稳定验收。

## 第二步：只把稳定规则写进 DESIGN.md

`DESIGN.md` 应记录后续页面仍会复用的规则，例如：

- 颜色、字体、间距、圆角和阴影
- 页面栅格、内容宽度和安全区
- 按钮、表单、空状态和反馈状态
- 响应式断点与窄屏降级方式
- 页面、共享组件和应用壳的职责边界

只在单次任务里出现的调试记录、截图路径、临时偏移量和命令输出，不应进入 `DESIGN.md`。设计稿没有明确表达的内容应标记为“推断”，不能写成确定规范。

## 第三步：先定位责任层，再修改代码

一个视觉问题通常可能属于四层：

| 层级 | 典型职责 | 常见误判 |
|------|------|------|
| 页面 | 当前业务布局、状态和交互 | 为修一个页面修改全局主题 |
| 共享组件 | 多页面复用的按钮、表单、弹窗、卡片 | 在每个调用方重复打补丁 |
| 应用壳 | 导航、背景、内容容器、安全区 | 把壳层默认样式当成页面样式 |
| 原生壳 | 系统控件、原生插件、安装包依赖 | 用 H5 效果证明原生能力已经完成 |

修改前应沿真实调用链确认责任层。根因在共享组件时修一次共享入口；需求只属于单页时，不把它上升成全局规则。

## 第四步：完成最小实现和静态检查

实现阶段只修改目标行为需要的文件，并运行项目已有的最小验证：

- 类型检查或编译
- 与改动相关的单元测试
- lint 或格式检查
- 必要的生产构建

这些检查证明代码能够通过工程门禁，但还不能证明页面与设计一致。

## 第五步：在真实运行界面验收

前端页面优先在应用内浏览器打开真实路由，按既定视口和状态逐项检查：

- 布局是否重叠、溢出或产生横向滚动
- 加载、完成、失败和空状态切换时是否跳动
- 文案、颜色、间距和控件状态是否符合设计依据
- 键盘焦点、点击区域和状态提示是否具备基本可访问性
- 控制台是否出现错误，关键请求是否符合预期

需要重复回归时，再把稳定路径写成 Playwright 断言。只有问题依赖真实账号、浏览器扩展或已有登录态时，才使用用户的 Chrome。

对于 App 专属能力，还要使用实际安装包和目标设备验证。浏览器中的 H5 页面正常，只能证明 Web 层成立。

---

## 一个典型修正案例

某个任务面板同时展示“月度状态”和“采集动作”，两处都在重复显示总数与进度。任务执行时临时插入一行状态，完成后又删除，导致下方列表上下跳动。

只调整配色不能解决这个问题。更合适的处理是：

1. 合并重复的信息，只保留一个主操作入口
2. 为执行状态保留固定高度的位置
3. 在等待、执行、完成和失败之间替换内容，而不是增删整个节点
4. 为动态状态增加 `role="status"` 和 `aria-live="polite"`
5. 分别用待执行、执行中、已完成和部分失败数据验收

这里的验收目标不是“最终截图好看”，而是状态变化全过程都稳定、可理解、可操作。

---

## 不要混淆完成状态

| 状态 | 可以说明什么 | 还不能说明什么 |
|------|------|------|
| 设计已确认 | 目标和边界明确 | 代码已经实现 |
| 代码已实现 | 修改已落到工程中 | 构建和运行正常 |
| 静态检查通过 | 类型、测试或构建门禁通过 | 真实页面符合设计 |
| 浏览器验收通过 | Web 页面在指定状态下符合预期 | App 原生能力有效 |
| 真机验收通过 | 指定安装包和设备路径成立 | 其他平台自动成立 |

交付总结应报告实际达到的层级，不要把较低层证据包装成更高层结论。

## 最小验收清单

- [ ] 已明确页面、平台、视口、数据状态和设计依据
- [ ] `DESIGN.md` 只记录稳定规则，推断项已标明
- [ ] 已确认问题属于页面、共享组件、应用壳还是原生壳
- [ ] 已运行最小静态检查
- [ ] 已在真实页面检查布局、状态切换和控制台
- [ ] 已验证至少一个桌面视口和一个移动视口
- [ ] App 专属能力已使用实际安装包和目标设备验证
- [ ] 交付结论准确说明当前达到的验收层级

## 经验总结

UI 交付不是“设计稿变成代码”，而是“设计依据变成可验证的运行行为”。

最关键的三条纪律是：先固定验收条件，再找对责任层，最后用真实运行证据收尾。这样既能避免 AI 在错误层级上反复打补丁，也能防止团队把测试通过误当成视觉和设备验收完成。
