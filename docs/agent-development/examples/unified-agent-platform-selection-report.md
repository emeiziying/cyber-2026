# 公司 Agent 技术现状、需求与平台演进规划

> **副标题：** Agent 方案分类、公司现状与选型方法
> **汇报对象：** 公司管理层、技术与业务负责人
> **资料快照：** 2026-08-21
> **文档性质：** 技术现状与规划汇报
> **汇报目标：** 统一 Agent 技术认知，说明公司现状、目标架构、方案差异和选型方法
> **范围说明：** 本报告不直接形成项目立项、预算、组织分工、具体 Runtime 选型或生产上线结论

---

## 领导摘要

### 五个核心判断

1. **Agent 不是单一产品。** 市场上的项目分别侧重应用平台、开发框架、工作流 Runtime、多 Agent、端侧 Harness 或评测治理，不能放在一张功能表中直接排名。
2. **公司已有早期基线，但尚未形成完整平台能力。** 当前 Dify、Agent BFF 和 Agent MCP 已支持早期问答、RAG 与只读工具调用；统一入口、资源授权、运行账本、审计、恢复和输出裁剪仍需补齐或验证。
3. **公司需要统一的是控制边界，不是所有实现。** 身份、租户、Agent API、模型、知识、工具、审计和运行治理应统一；具体 Runtime、语言和领域算法可以按场景选择。
4. **目标架构应保持 Runtime 可替换。** 业务系统依赖公司掌握的统一 Agent API，Runtime 负责模型调用和流程编排，业务后端继续负责最终权限、正式计算、批准和执行。
5. **选型必须从业务场景出发。** 先用硬约束缩小候选范围，再比较完整方案；只有资料分析无法回答的关键问题才需要验证，不做脱离场景的框架总排名。

### 当前总体建议

- 将统一 Agent 平台作为公司级能力持续规划，但避免重做候选产品已有的 Agent loop、编辑器和工作流能力。
- 将 Dify 视为当前早期实现基线，并按与其他候选相同的硬约束核验；未验证项不能视为通过。证据满足目标工作负载时可以保留，存在阻断或明确缺口时再比较替代方案。
- 中心平台与端侧 Agent 分成两条路线：中心平台解决公司业务系统接入，DeepSeek Harness 等端侧 Harness 仅作为未来桌面 Agent 的独立研究对象。
- 电力交易多 Agent 先解决只读分析、证据归一化和确定性聚合，不让 LLM 直接决定金额、风险或交易执行。
- TypeScript 与 Python 按职责并存，通过统一 Agent API、MCP 和业务 API 隔离，而不是为了技术统一重写现有能力。

## 公司当前与未来需求

### 需求分层

| 阶段或场景 | 主要需求 | 对平台的要求 |
|------------|----------|--------------|
| 近期业务接入 | AI 问答、知识检索、只读工具调用、嵌入现有业务系统 | 统一身份、Agent API、会话归属、RAG 权限、流式响应和审计 |
| 中期复杂应用 | 结构化输出、复杂流程、暂停恢复、人工确认、版本回放和评测 | 状态持久化、恢复、幂等、可观测、质量与成本治理 |
| 电力交易分析 | 政策、市场数据、预测和策略等多 Agent 结果统筹 | 只读 Agent、证据 Schema、确定性聚合、风险门禁和人工接管 |
| 未来端侧能力 | 本地文件、桌面应用和受控本地工具 | 设备身份、目录与进程隔离、凭据、策略、升级、撤销和审计回传 |

### 长期不变的业务边界

无论选择何种 Agent 平台或 Runtime，以下能力继续由确定性代码和业务系统承担：

- 用户、租户和业务资源的最终授权；
- 金额、敞口、收益、额度、规则和风险计算；
- 正式批准、交易命令、幂等、补偿和对账；
- 对真实业务数据和写操作的最终审计责任。

Agent 主要用于理解意图、检索资料、组织证据、生成候选分析和解释结果。

## Agent 技术分类与方案差异

### 不同类别解决什么问题

| 技术类别 | 主要交付物 | 代表项目 | 更适合的场景 |
|----------|------------|----------|----------------|
| AI 应用平台 | 可视化应用、RAG、Workflow、发布和运营 | Dify、Haystack Enterprise | 快速建设问答、知识应用和标准流程 |
| 可视化开发与 Runtime | 组件画布、Flow 设计、API 和运行服务 | Langflow；Flowise（已归档，仅作历史参考） | 可视化开发、流程实验和生产 Runtime 候选 |
| Agent Framework | Agent loop、工具、结构化输出和模型抽象 | Mastra、PydanticAI、LangChain | 代码优先的后端 Agent 服务 |
| Workflow Runtime | 状态图、检查点、暂停恢复和长任务控制 | LangGraph、Microsoft Agent Framework | 审批、长流程、人工确认和故障恢复 |
| 多 Agent Framework | 角色协作、委派和任务编排 | CrewAI、AgentScope、Google ADK | 分工明确的分析和业务自动化 |
| Agent Harness | 上下文、工具、Session、运行骨架和本地能力 | DeepSeek Harness、Claude Agent SDK | Coding Agent、端侧 Agent 和可扩展运行环境 |
| 可观测与评测 | Trace、质量、成本和回归 | LangSmith、Langfuse、Phoenix | 生产治理和效果评估 |

类别会重叠：一个项目可能同时包含 Framework、Workflow 和部署能力。分类目的是识别主要交付物，不是给产品贴唯一标签。

### 代表性路线对比

| 路线 | 代表方案 | 主要优势 | 需要补充或验证 | 与公司需求的关系 |
|------|----------|----------|------------------|------------------|
| 低代码 AI 应用平台 | Dify | 问答、RAG、Workflow 和发布路径完整，上手快 | 复杂工程控制、跨 Runtime 合同、企业治理和长期恢复能力需按场景验证 | 当前早期实现基线，可保留也可替换 |
| 可视化开发与 Runtime | Langflow | 可视化 IDE、API 和生产 Runtime 路径兼顾原型与部署 | 具体版本、认证、SSO/RBAC、Helm 形态及公司控制面集成需按完整方案验证 | 可进入可视化开发和生产 Runtime 候选池，但不单独等同于公司控制面 |
| TypeScript 代码优先 | Mastra | Agent、Workflow、MCP 和服务端工程集成较自然 | 企业控制面、版本边界、耐久执行和完整运维成本需验证 | 新建复杂 TS Agent 服务的候选，不是既定路线 |
| Python 代码优先与工作流 | LangGraph、PydanticAI、Microsoft Agent Framework | Python 生态、类型化工具、状态图和长流程能力丰富 | 业务前端、平台控制面及不同组件组合需要公司集成 | 适合数据、算法、复杂流程和 Python 团队 |
| Python 一体化 Runtime | Agno | Agent、Team、Workflow、API Runtime 和前端路径相对集中 | 开源与商业控制面边界、升级稳定性和耐久执行能力需验证 | 可作为 Python 平台型候选研究 |
| 角色协作与 Flow | CrewAI OSS + 可选 AMP | Crews 与 Flows 兼顾角色协作和流程控制，AMP 提供进一步平台能力 | OSS、AMP、前端和部署形态必须作为不同完整方案比较 | 多角色业务自动化和流程型 Agent 候选 |
| 多 Agent Runtime | AgentScope 2.0 + Studio | 多 Agent、Runtime、沙箱、AaaS、部署与 OTel 可观测路径较完整 | Studio 与企业 SSO、RBAC、租户和控制面的边界需验证 | 复杂多 Agent 引擎和研发平台候选 |
| 端侧 Harness | DeepSeek Harness | 本地文件、工具、插件和会话运行骨架 | Developer Preview；认证、设备治理、隔离和企业控制面不足 | 未来桌面 Agent 候选，不适合作为中心平台基座 |

更完整的分类、比较单位和语言分工见[附件 A：Agent 技术分类与方案对比](./unified-agent-platform-attachments/appendix-a-technology-selection)。

## 公司当前架构与成熟度

### 当前能力判断

| 事项 | 当前事实 | 主要差距 |
|------|----------|----------|
| 业务入口 | 业务前端直接调用 Agent BFF | 尚未经过 Gateway 统一入口 |
| 身份 | Agent BFF 在线查询 Gateway 身份 | 身份断言、资源绑定和防重放合同尚未冻结 |
| Runtime | Dify 承接早期问答、RAG 和流程 | 当前实现不等于长期选型结论 |
| 工具 | Agent MCP 接入业务后端只读能力 | 工具逐次授权、资源级授权和完整审计仍需验证 |
| 会话 | Dify 保存会话和消息，Agent BFF 无数据库 | 平台 Run 账本、跨 Runtime 会话合同和恢复能力待建设 |
| 流式输出 | Agent BFF 对上游 SSE 进行字节转发 | 事件和字段白名单裁剪尚未实现 |
| 运行证据 | 已有开发代码路径 | 部署、强制执行和正负向验证证据须分别登记 |

### 当前链路

~~~text
业务前端
  → Agent BFF
      ├─ 调用业务 Gateway current-user 在线校验身份
      └─ 校验通过后调用 Dify
          ├─ 普通问答 / RAG：直接返回响应
          └─ 需要工具时：Agent MCP
                           → 业务 Gateway（按接入合同可选）
                           → 业务后端
~~~

Agent BFF 目前不仅转换会话用户 ID，还承担 Dify 密钥隔离、App 与 Agent 映射、输入白名单、稳定用户标识、短期 MCP 委托和 SSE 转发。它可以演进为统一 Agent API 的起点，但当前能力不能直接视为完整平台控制面。

### 成熟度口径

| 状态 | 含义 |
|------|------|
| Implemented | 在指定源码版本中存在实现 |
| Deployed | 在指定环境和配置版本中已部署 |
| Enforced | 无法通过旁路绕过 |
| Verified | 已通过冻结的正向、负向和故障测试 |

“已实现”不能代替“已部署、已强制、已验证”。详细证据口径见[附件 F](./unified-agent-platform-attachments/appendix-f-evidence-sources)。

## 目标平台架构与职责边界

### 目标逻辑架构

~~~text
现有业务系统 / 统一 AI 入口
            │
       API Gateway
  认证、路由、限流、可信身份传递
            │
      统一 Agent API
资源授权、会话归属、Run、审计、Runtime 适配
            │
      可替换 Agent Runtime
       ├── 公司模型网关 ── 获批模型
       ├── 知识访问门 ──── 获授权索引与内容源
       └── MCP / 受控业务 API
             工具白名单、逐次授权、协议适配
                       │
                   业务后端
        最终权限、正式计算、批准、执行与对账
~~~

模型网关和知识访问门表示必须落实的逻辑治理责任，可以复用现有能力或合并部署，不要求单独建设两个新系统。

### 各层责任

| 层次 | 核心责任 | 不承担 |
|------|----------|--------|
| API Gateway | 认证、路由、粗粒度限流、清除外部身份 Header、传递可信身份 | Agent 业务编排 |
| 统一 Agent API | Agent 和资源授权、会话归属、Run/SSE、审计、Runtime 适配 | 最终业务数据授权 |
| Agent Runtime | Agent loop、Workflow、模型调用和结构化输出 | 身份源、最终业务授权和交易执行 |
| 模型网关与知识访问门 | 模型白名单、数据分级、用量控制、知识 ACL 和版本 | 接受模型自行声明的租户或数据范围 |
| MCP / 受控业务 API | 工具目录、短期委托、逐次调用授权和协议适配 | Runtime 直连原始业务后端，或替代对象级权限 |
| 业务后端 | 最终数据权限、正式计算、规则、风控、批准、幂等、执行和对账 | 把正式结论交给 LLM 决定 |

### 设计原则

- 业务前端依赖稳定的统一 Agent API，不依赖具体 Runtime 的密钥、内部用户标识或私有事件。
- 用户、租户和业务资源只来自服务端可信上下文，不能由模型、Prompt 或普通输入决定。
- 当前 Agent BFF 可以演进为统一 Agent API，不新增只做透传的重复服务。
- Runtime 保持可替换，但不提前建设兼容所有框架的复杂插件体系。
- 中心平台与端侧 Agent 共用身份、模型、工具和审计原则，但分别选型和演进。

详细逐跳信任与审计边界见[附件 B：最小安全合同](./unified-agent-platform-attachments/appendix-b-security-contract)。

## Agent 方案如何选型

### 五步选型方法

1. **定义工作负载。** 明确业务问题、输入输出、允许动作、依赖系统、价值指标和失败后果。
2. **使用硬约束筛选。** 先检查私有化、数据安全、身份、许可证、技术栈、运行环境和运维边界。
3. **比较完整方案。** 比较“项目及版本 + Edition + 部署形态 + 外接组件 + 公司自建能力”，不只比较 SDK 功能列表。
4. **验证关键不确定性。** 在相同数据、模型、工具、权限和资源条件下，只验证资料分析无法确认的能力。
5. **形成场景级结论。** 综合业务效果、安全、恢复、工程复杂度、运维、成熟度和完整 TCO，不形成脱离工作负载的通用排名。

### 主要比较维度

| 维度 | 重点问题 |
|------|----------|
| 业务适配 | 是否支持问答、RAG、工具、复杂流程、多 Agent 或端侧工作负载 |
| 工程控制 | 代码优先还是低代码；Schema、测试、版本、调试和扩展方式是否匹配团队 |
| 状态与恢复 | 会话、检查点、暂停、恢复、重试和副作用幂等达到什么程度 |
| 企业治理 | 身份、租户、资源授权、模型与 RAG 访问、工具审批和审计是否可落地 |
| 平台完整度 | Runtime、API、前端、控制面、评测、部署和运维需要外接多少组件 |
| 成熟度与成本 | 许可证、版本稳定性、升级、社区或厂商支持、资源和完整 TCO |

### POC 在选型中的位置

POC 只是可选验证手段，不是所有候选都要做，也不是本报告的中心目标：

- 许可证、语言、部署形态和明显缺失能力可通过资料分析直接排除；
- 对状态恢复、SSE、工具授权、多 Agent 协作和端侧隔离等关键不确定性，可进行范围受控的验证；
- 验证只回答预先定义的问题，不能自动产生生产选型结论。

验证方法与证据模板见[附件 C：Agent 方案验证与选型证据模板](./unified-agent-platform-attachments/appendix-c-selection-validation)。

### TypeScript 与 Python

| 责任 | 当前建议 |
|------|----------|
| 当前 Agent BFF、Agent MCP 和领域能力 | 延续 Python，不为候选框架重写现有边界 |
| 业务 Gateway 与前端 | 延续现有技术栈，通过统一 Agent API 隔离 Runtime |
| 预测、优化、量化和数据处理 | 保留 Python，通过 MCP 或业务 API 服务化 |
| TypeScript Runtime | 在明确需要代码优先 TS 工程路线时评估 |
| Python Runtime | 在需要 Python 编排、数据生态或耐久工作流时评估 |
| 端侧 Runtime | 使用候选原生技术栈，但必须满足统一身份、安全和审计合同 |

语言本身不单独计分。新增技术栈必须把 CI/CD、供应链、观测、值班和人员能力计入完整方案。

## 场景与当前选型建议

| 场景 | 当前建议 | 何时重新评估 |
|------|----------|--------------|
| 统一公司控制面 | 优先形成 Gateway 后的统一 Agent API、模型/RAG/工具受控路径和审计合同 | 公司身份、资源、运行和审计边界发生变化时 |
| 现有问答与 RAG | 将 Dify 作为可替换基线，按统一硬约束补齐现状证据；未验证项不能作为生产通过 | 生产晋级、规模扩张、目标工作负载变化，或出现能力、治理、恢复和成本缺口时 |
| 新建 TS 代码优先服务 | Mastra 等作为候选，不预先确定为公司主 Runtime | 出现低代码难以表达的复杂工程需求时 |
| Python 复杂流程 | LangGraph、PydanticAI、Agno 或 Microsoft Agent Framework 按工作负载比较 | 需要状态图、持久恢复、算法或 Python 生态时 |
| 电力交易多 Agent | 先采用只读专业 Agent、证据归一化、确定性聚合和风险门禁 | 只读仿真证据充分后，再讨论更高风险能力 |
| 员工端侧 Agent | DeepSeek Harness 等作为独立研究方向，不作为中心平台基座 | 设备治理、隔离、认证和版本稳定性达到要求时 |

不建议为了展示“平台可替换”而同时建设两套 Runtime，也不建议让某个热门框架覆盖所有工作负载。电力交易多 Agent 的具体边界见[附件 E](./unified-agent-platform-attachments/appendix-e-electricity-multi-agent)，DeepSeek Harness 的定位见[附件 D](./unified-agent-platform-attachments/appendix-d-deepseek-harness)。

## 平台演进规划

| 阶段 | 规划重点 | 启动依据 |
|------|----------|----------|
| 近期 | 稳定现有问答和只读工具链路；登记实现、部署、强制与验证状态；补齐已知安全缺口 | 当前业务接入和风险整改需求 |
| 中期 | 将业务入口纳入 Gateway；形成统一 Agent API、Run 账本、Runtime 适配和模型/RAG/工具审计 | 接入业务增加，重复建设开始显现 |
| 按需选型 | 先用统一标准核验当前基线；对未通过、存在关键不确定性或工作负载不同的范围评估替代方案 | 生产晋级、规模扩张、目标场景变化，或形成可复核缺口 |
| 场景扩展 | 电力交易先推进只读分析与确定性聚合；端侧 Agent 独立研究 | 场景价值、数据边界和风险控制明确 |
| 生产治理 | 持续补齐容量、容灾、灰度、升级、成本、评测和安全响应 | 候选范围和生产工作负载明确 |

该规划描述技术演进顺序，不预设具体项目、预算、组织角色或实施排期。

## 主要风险与管理关注点

| 风险 | 典型表现 | 管理关注点 |
|------|----------|------------|
| 身份、数据或执行边界失守 | 模型或客户端改变租户、资源、工具或执行范围 | 服务端绑定身份和资源；工具逐次授权；业务后端保留最终权限 |
| 平台范围扩张但价值不清 | 同时建设编辑器、Runtime、控制台、端侧和多 Agent | 从业务场景出发，优先统一不可替代的控制边界 |
| 当前实现或热门框架过早固化 | 将 Dify、Mastra、DeepSeek Harness 等直接定为公司标准 | 完整方案比较；保留可替换 API；按工作负载形成结论 |
| 技术试验代替生产证据 | Demo 成功即认为安全、可恢复、可运维 | 区分 Implemented、Deployed、Enforced 和 Verified |

本次汇报旨在统一 Agent 技术分类、公司现状、目标架构和选型方法。具体项目、候选验证和生产选型应在业务场景明确后分别评估。
