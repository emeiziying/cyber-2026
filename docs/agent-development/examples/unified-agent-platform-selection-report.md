> **资料快照：** 2026-08-24
> **文档性质：** 技术现状与规划汇报
> **汇报目标：** 统一 Agent 技术认知，说明公司现状、目标架构、方案差异和选型方法

> **待决事项：** 具体 Agent 执行后端（Runtime）、实施排期、预算、组织分工和生产上线结论按场景另行决策

## 领导摘要

### 五个核心判断

1. **Agent 不是单一产品。** 市场方案分别侧重应用开发与运营、代码开发框架、可恢复工作流、多 Agent 协作、端侧运行骨架或评测治理，不能放在一张功能表中直接排名。
2. **公司已有早期基线，但尚未形成完整平台能力。** 当前源码已形成 Dify、Agent BFF 和 Agent MCP 的早期问答、检索增强生成（RAG）与只读工具调用链路，但是否已经部署到目标环境、是否能够防止旁路绕过、是否完成测试验证，尚未形成闭环；统一入口、资源授权、Agent 运行记录（Run 账本）、业务审计、失败恢复和面向客户端的安全输出仍存在功能缺口或证据缺口。
3. **公司需要统一的是控制边界，不是所有实现。** 身份、租户、Agent API、模型、知识、工具、审计和运行治理应统一；具体执行后端、语言和领域算法可以按场景选择。
4. **目标架构应保持 Agent 执行后端可替换。** 业务系统依赖公司掌握的统一 Agent API，执行后端负责模型调用和流程编排，业务后端继续负责最终权限、正式计算、批准和执行。
5. **选型必须从业务场景出发。** 先用硬约束缩小候选范围，再比较完整方案；只有资料分析无法回答的关键问题才需要验证，不做脱离场景的框架总排名。

### 当前总体建议

- 统一 Agent 平台建设方向已经确定：近期优先评估以现有 Agent BFF 为基础形成最小统一 Agent API，先明确并版本化身份与资源授权、一次运行记录（Run）、流式输出（SSE）和工具调用（MCP）的接口约定；暂不重建候选产品已有的通用 Agent 执行内核、编辑器和工作流能力。
- 将 Dify 视为当前早期实现基线，并按与其他候选相同的硬约束核验；未验证项不能视为通过。证据满足目标工作负载时可以保留，存在阻断或明确缺口时再比较替代方案。
- 中心平台与端侧 Agent 分成两条路线：中心平台解决公司业务系统接入，DeepSeek Harness 等端侧运行骨架仅作为未来桌面 Agent 的独立研究对象。
- 电力交易多 Agent 如进入建设，先限定为只读分析、统一证据格式和固定规则汇总；金额、风险和交易执行继续由业务系统决定。
- TypeScript 与 Python 按职责并存，通过统一 Agent API、MCP 和业务 API 隔离，而不是为了技术统一重写现有能力。

### 本次汇报的决策边界

- **需要形成共识：** 统一控制边界优先、Agent 执行后端可替换、服务端与端侧分线、业务后端保留最终权限和执行责任。
- **当前无需决定：** 不要求现在选择 Mastra、Agno、LangGraph、Langflow 或其他执行后端，也不因现有 Dify 实现直接形成长期标准。
- **后续决策方式：** 当现有方案拟进入生产、扩大使用规模、工作负载变化或形成可复核缺口时，再输出场景级候选清单、验证证据和架构决策记录（ADR）。

## 公司当前与未来需求

### 需求分层

| 阶段或场景 | 主要需求 | 对平台的要求 |
|------------|----------|--------------|
| 近期业务接入 | AI 问答、知识检索、只读工具调用、嵌入现有业务系统 | 统一身份、Agent API、会话归属、RAG 权限、流式响应和审计 |
| 中期复杂应用 | 结构化输出、复杂流程、暂停恢复、人工确认、版本与输入可追溯、限定范围重放和评测 | 状态持久化、恢复、幂等、可观测、质量与成本治理 |
| 电力交易分析 | 政策、市场数据、预测和策略等多 Agent 结果统筹 | 只读 Agent、统一证据格式（Schema）、固定规则汇总、风险校验和人工接管 |
| 未来端侧能力 | 本地文件、桌面应用和受控本地工具 | 设备身份、目录与进程隔离、凭据、策略、升级、撤销和审计回传 |

### 长期不变的业务边界

无论选择何种 Agent 平台或执行后端（Runtime），以下能力继续由确定性代码和业务系统承担：

- 用户、租户和业务资源的最终授权；
- 金额、敞口、收益、额度、规则和风险计算；
- 正式批准、交易命令、幂等、补偿和对账；
- 对真实业务数据和写操作的最终审计责任。

Agent 主要用于理解意图、检索资料、组织证据、生成候选分析和解释结果。

## Agent 技术路线与产品形态

### 本文如何定义这些名词

本文分类不是行业统一标准，而是面向选型的工作定义。判断依据是：引入该项目后，它主要替团队交付什么、承担什么责任；项目自身的宣传称谓只作参考。

| 技术路线或产品形态 | 本文工作定义 | 关键边界 |
|--------------------|--------------|----------|
| AI 应用开发与运营平台 | 覆盖 AI 应用创建、RAG、流程配置、调试、发布、API 和基础运营的产品 | 候选产品的应用运营面不等于公司统一 Agent 控制面 |
| 可视化 Flow IDE / Runtime | 用组件画布定义、调试 Flow，并通过 API 或服务执行 Flow 的开发环境与运行服务 | 有画布和 HTTP Server 不等于具备企业多租户、业务授权和审计 |
| Agent SDK / Framework | 供开发者用代码实现 Agent 的模型、工具、循环执行、记忆（Memory）和结构化输出等抽象 | 通常不直接承担宿主应用的身份、部署、数据库和生产运维 |
| Workflow Runtime（耐久工作流执行引擎） | 执行长时间、有状态流程，提供检查点、重试、暂停、恢复和人工介入 | 重点是可靠执行，不一定提供 RAG、应用发布或完整开发平台 |
| 多 Agent 协作框架 | 在 Agent Framework 或 Workflow 之上提供角色、委派、任务交接（handoff）、并行协作和结果汇总 | 是协作模式的特化能力，不代表所有任务都应拆成多个 Agent |
| Agent Harness（运行骨架） | 将 Agent 循环、默认 Prompt、上下文、工具、会话（Session）和扩展机制装配成可直接运行的环境 | 更适合开放式长任务、Coding 或端侧场景，不等于企业中心平台 |
| 可观测与评测工具 | 采集调用链（Trace）、成本、延迟和质量数据，并支持数据集实验、评分与回归 | 属于横向治理能力，不能替代业务审计、授权或 Agent 执行 |

Framework、Workflow Runtime 和 Harness 的基本区分参考了[LangChain 当前公开采用的一种概念用法](https://docs.langchain.com/oss/python/concepts/products)：Framework 提供开发抽象，Workflow Runtime 侧重有状态、可恢复执行，Harness 提供带默认工具和上下文管理的完整运行骨架。类别之间允许重叠；后文“Runtime”只表示可替换执行后端这一架构角色，真正承担该角色的是由应用平台或 Framework、运行服务及宿主基础设施组成的完整方案。

### 行业方案举例（不代表入围或推荐名单）

是否进入场景级候选清单，仍须通过许可证、部署、安全、技术栈和运维边界等硬约束筛选。

| 路线 | 代表方案 | 与公司需求的关系 |
|------|----------|------------------|
| 低代码 AI 应用平台 | Dify | 当前问答、RAG 和标准流程的早期基线，根据证据决定保留或替换 |
| 可视化开发与 Runtime | Langflow | 可视化开发和 Python Runtime 候选，不单独等同于公司控制面 |
| TypeScript 代码优先 | Mastra | 新建复杂 TS Agent 服务候选，不是既定路线 |
| Python 与多语言代码优先/工作流 | LangGraph、PydanticAI、Microsoft Agent Framework（C#、Python、Go） | 适合数据、算法、复杂流程和多语言团队 |
| Python 一体化 Runtime | Agno | Python 平台型候选，开源 Runtime 与托管控制面需分别核验 |
| 角色协作与 Flow | CrewAI OSS + 可选 CrewAI AMP（商业平台） | 多角色业务自动化候选，OSS 与 AMP 作为不同方案比较 |
| 多 Agent Runtime | AgentScope 2.0 + Studio | 复杂多 Agent 引擎和研发平台候选，企业治理边界需核验 |
| 端侧 Harness | DeepSeek Harness | 未来桌面 Agent 研究候选，不作为中心平台基座 |

更完整的分类、完整方案比较和语言分工见[Agent 技术栈选型](./agent-technology-selection)。

## 公司当前架构与成熟度

### 当前能力判断

| 事项 | 源码观察 | 主要差距 | 证据状态 |
|------|----------|----------|----------|
| 业务入口 | 业务前端直接调用 Agent BFF | 尚未经过 Gateway 统一入口 | 源码：已观察；部署/不可绕过/测试：未核验 |
| 身份 | Agent BFF 在线查询 Gateway 身份 | 可信身份传递、资源绑定，以及防止旧凭据被重复使用的约定尚未明确并验证 | 源码：已观察；部署/不可绕过/测试：未核验 |
| Runtime | Dify 承接早期问答、RAG 和流程 | 当前实现不等于长期选型结论 | 源码：已观察；部署/不可绕过/测试：未核验 |
| 工具 | Agent MCP 接入业务后端只读能力 | 工具逐次授权、资源级授权和完整审计仍需验证 | 源码：已观察；部署/不可绕过/测试：未核验 |
| 会话 | 代码将会话和消息持久化委托给 Dify，Agent BFF 无数据库 | 目标环境实际落盘、平台 Run 账本、跨 Runtime 会话合同和恢复能力待核验或建设 | 源码：已观察；部署/不可绕过/测试：未核验 |
| 流式输出 | Agent BFF 对上游 SSE 进行字节转发 | 事件和字段白名单裁剪尚未实现 | 源码：已观察；部署/不可绕过/测试：未核验 |

“源码：已观察”只表示当前检出代码中存在对应路径，不代表目标环境已经具备该能力；进入生产决策前还应留存源码版本、关键路径和验证证据。

### 源码实现链路（部署、是否不可绕过及测试结果待核）

~~~text
业务前端
  → Agent BFF
      ├─ 调用业务 Gateway current-user 在线校验身份
      └─ 校验通过后调用 Dify
          ├─ 普通问答 / RAG：直接返回响应
          └─ 需要工具时：Agent MCP（验证委托、限制工具范围）
                           → 业务 Gateway（是否经过取决于部署拓扑）
                           → 业务后端（最终授权与审计不可省略）
~~~

源码观察显示，Agent BFF 除转换会话用户 ID 外，还处理 Dify 密钥隔离、App 与 Agent 映射、输入白名单、稳定用户标识、短期 MCP 委托和 SSE 转发；这些控制是否已部署、不可绕过并通过测试尚未确认。后续建设可优先评估在此基础上演进统一 Agent API，避免新建只做重复转发的服务。

### 成熟度口径

`Implemented`（源码实现）、`Deployed`（环境部署）、`Enforced`（在已记录的入口和信任边界内不可旁路）和 `Verified`（测试验证）是四个独立证据门，分别记录“通过、未通过或未验证”。详细定义和留痕要求见[附件 C](./unified-agent-platform-attachments/appendix-c-evidence-sources)。

## 目标平台架构与职责边界

### 目标逻辑架构

~~~text
现有业务系统 / 统一 AI 入口
            │
       API Gateway
  认证、路由、限流、可信身份传递
            │
      统一 Agent API
入口授权、会话归属、Agent 运行记录、审计、执行后端适配
            │
      可替换 Agent 执行后端（Runtime 角色）
       ├── 公司模型网关 ── 获批模型
       ├── 知识访问门 ──── 获授权索引与内容源
       └── MCP / 受控业务 API
             工具白名单、逐次授权、协议适配
                       │
                   业务后端
        最终权限、正式计算、批准、执行与对账
~~~

图中各方框表示必须明确归属的逻辑责任，不代表必须分别新建系统；相关能力可以复用、合并部署或采购，具体物理部署形态另行设计。

### 各层责任

| 层次 | 核心责任 | 不承担 |
|------|----------|--------|
| API Gateway | 认证、路由、粗粒度限流；剥离客户端身份请求头（Header），并根据已验证凭据重建服务端可信身份 | Agent 业务编排 |
| 统一 Agent API | 校验用户对 Agent、会话、知识和工具入口的权限；维护 Run/SSE、签发短期工具委托、审计和 Runtime 适配 | 具体业务对象和动作的最终授权 |
| Agent 执行后端（Runtime） | Agent 循环执行、工作流编排、模型调用和结构化输出 | 身份源、最终业务授权和交易执行 |
| 模型网关与知识访问门 | 模型白名单、数据分级、用量控制、知识访问控制（ACL）和版本 | 接受模型自行声明的租户或数据范围 |
| MCP / 受控业务 API | 验证短期委托，逐次校验工具白名单和服务端资源上下文，并完成协议适配 | 接受模型自行声明的身份或资源范围，或替代业务对象级最终授权 |
| 业务后端 | 对具体业务对象和动作重新执行最终授权，并承担正式计算、规则、风控、批准、幂等、执行、对账和业务审计 | 把正式结论交给 LLM 决定 |

Agent 运行记录、技术追踪和业务审计不是一回事：统一 Agent API 保存调用主体、策略版本、运行状态和安全输出记录，Runtime 保存调试与运维 Trace，业务后端保存授权、数据访问、批准和执行记录；三者通过运行和业务引用标识关联。统一 Agent API 对客户端保存和回放面向用户的脱敏投影，Runtime 内部会话与检查点另按最小化、访问控制、加密和保留期限治理。

### 设计原则

- 业务前端依赖稳定的统一 Agent API，不依赖具体执行后端的密钥、内部用户标识或私有事件。
- 用户、租户和业务资源只来自服务端可信上下文，不能由模型、Prompt 或普通输入决定。
- 优先评估现有 Agent BFF 能否演进为统一 Agent API，不新增只做透传的重复服务。
- 执行后端可替换是指业务系统依赖稳定外部接口，新 Run 可以切换后端；不承诺在途 Run、检查点或内部记忆能够跨 Runtime 迁移，也不提前建设兼容所有框架的复杂插件体系。
- 中心平台与端侧 Agent 共用身份、模型、工具和审计原则，但分别选型和演进。

上述内容是汇报级职责边界；进入具体项目后，再明确每一跳之间的身份、授权、数据、错误处理约定和验收项。

### 服务端平台与端侧 Agent 的建设重点

| 路线 | 主要目标 | 公司必须掌握 | 优先复用开源项目 |
|------|----------|--------------|------------------|
| 服务端 Agent 平台 | 为多个业务系统提供统一 Agent 服务 | 统一 Agent API、可信身份与业务资源绑定、Run 账本、每次工具调用授权、业务审计和面向客户端的安全输出 | Agent 循环执行、工作流、多 Agent、RAG、记忆、技术追踪（Trace）、评测和开发工作台（Studio） |
| 端侧 Agent | 在员工电脑上安全使用本地文件、应用和工具 | 设备身份、中央策略、凭据代理、远程撤销、脱敏审计、签名分发和升级回滚 | 本地 Runtime、会话、工具、插件、基础 UI、审批和沙箱能力 |

“公司必须掌握”是指责任、规则、接口和审计证据不能失控，不等于所有能力都由公司从零开发。服务端与端侧可以共用公司级身份、模型、工具和审计规则；由于运行环境与安全要求不同，两条路线原则上分别选型，是否复用同一产品须独立验证。详细功能清单、开源项目覆盖范围和公司自建边界见[附件 D](./unified-agent-platform-attachments/appendix-d-server-endpoint-capability-matrix)。

## Agent 方案如何选型

### 五步选型方法

1. **定义工作负载。** 明确业务问题、输入输出、允许动作、依赖系统、价值指标和失败后果。
2. **使用硬约束筛选。** 先检查私有化、数据安全、身份、许可证、技术栈、运行环境和运维边界。
3. **比较完整方案。** 比较“项目及版本 + 开源/企业版本（Edition）+ 部署形态 + 外接组件 + 公司自建能力”，不只比较 SDK 功能列表。
4. **验证关键不确定性。** 在相同数据、模型、工具、权限和资源条件下，只验证资料分析无法确认的能力。
5. **形成场景级结论。** 综合业务效果、安全、恢复、工程复杂度、运维、成熟度和总体拥有成本（TCO），不形成脱离工作负载的通用排名。

### 主要比较维度

| 维度 | 重点问题 |
|------|----------|
| 业务适配 | 是否支持问答、RAG、工具、复杂流程、多 Agent 或端侧工作负载 |
| 工程控制 | 代码优先还是低代码；Schema、测试、版本、调试和扩展方式是否匹配团队 |
| 状态与恢复 | 会话、检查点、暂停和恢复达到什么程度；重试是否会重复产生写入、扣费等副作用 |
| 企业治理 | 身份、租户、资源授权、模型与 RAG 访问、工具审批和审计是否可落地 |
| 平台完整度 | Runtime、API、前端、控制面、评测、部署和运维需要外接多少组件 |
| 成熟度与成本 | 许可证、版本稳定性、升级、社区或厂商支持、资源和完整 TCO |

### Dify、Langflow、Mastra 与 Agno 的定位比较

四者都可以承担 Agent 执行后端的部分职责，但不是同一种产品：Dify 侧重低代码应用交付，Langflow 侧重 Python 可视化开发与 Flow Runtime，Mastra、Agno 侧重代码优先编排和多 Agent。当前不形成四选一总排名，也不把其中任何项目视为已经完成初筛的正式短名单。

四者的产品形态、RAG、多 Agent、上下文、恢复、评测、前端、许可证和公司自建边界见[附件 F：Dify、Langflow、Mastra 与 Agno 选型对比](./unified-agent-platform-attachments/appendix-f-dify-langflow-mastra-agno-comparison)。

### 概念验证（POC）在选型中的位置

POC 只用于验证资料无法回答的决策性问题，不是所有候选的必经步骤，也不能自动产生生产选型结论；具体设计见[Agent 技术栈选型的“最小 POC 设计”](./agent-technology-selection#最小-poc-设计)。

### TypeScript 与 Python

| 责任 | 当前建议 |
|------|----------|
| 现有 Agent BFF 和 Agent MCP | 保持当前 Python 实现，除非单项重构另行决策 |
| 业务 Gateway 与前端 | 延续现有技术栈，通过统一 Agent API 隔离 Runtime |
| 新建领域能力 | 按具体场景选择语言，通过 MCP 或业务 API 服务化；本表不构成公司级语言标准 |
| 预测、优化、量化和数据处理 | 可优先使用 Python 生态，通过 MCP 或业务 API 服务化 |
| TypeScript 执行后端 | 在明确需要代码优先 TS 工程路线时评估 |
| Python 执行后端 | 在需要 Python 编排、数据生态或耐久工作流时评估 |
| 多语言工作流执行后端 | 在 C#、Go、Python 或 Microsoft 生态成为硬约束时评估 |
| 端侧执行后端 | 使用候选原生技术栈，但必须满足统一身份、安全和审计约定 |

语言本身不单独计分。新增技术栈必须把 CI/CD、供应链、观测、值班和人员能力计入完整方案。

作为生态参考，截至 2026-08-24，本报告覆盖的 28 个活跃开源核心实现中，Python 占 50.0%、TypeScript 占 39.3%、Go / .NET 等其他语言占 10.7%；只比较 Python 与 TypeScript 时为 56.0% : 44.0%。服务端样本更偏 Python，端侧 / Coding Harness 小样本更偏 TypeScript；这不是商业市场份额，也不能替代场景选型。统计口径和逐项目数据见[附件 E](./unified-agent-platform-attachments/appendix-e-agent-language-ecosystem)。

## 场景与当前建议视图

| 场景 | 当前建议 | 暂不做 | 下次决策触发 | 届时输出 |
|------|--------|--------|--------------|----------|
| 统一公司控制面 | 优先评估从现有 BFF 演进最小统一 Agent API；明确并版本化 Gateway 接入、身份与资源、Run/SSE、模型/RAG/工具和审计约定 | 不新建只做透传的重复服务，不提前适配全部执行后端 | 首个生产接入或多业务复用边界明确 | 阶段实施范围、接口约定与验收证据 |
| 现有问答与 RAG | 将 Dify 作为可替换基线，先完成源码、部署、不可绕过和测试四类证据核验；缺失能力是否建设另行决策 | 不一次性重写，也不直接固化为公司标准 | 拟进入生产、扩大使用规模、工作负载变化，或形成能力、治理、恢复和成本缺口 | 保留或替换 Dify 的场景级 ADR |
| 新建复杂服务端 Agent | 先定义工作负载和硬约束 | 不预先指定 Mastra、Agno、LangGraph、Langflow 或其他主执行后端 | 出现低代码难以测试、版本化或维护的流程，或明确需要状态恢复、算法和多语言能力 | 同赛道候选清单、验证证据和执行后端 ADR |
| 电力交易多 Agent | 如启动该场景，先限定为只读专业 Agent、统一证据格式、固定规则汇总和风险校验 | 不让 LLM 决定金额、风险或交易执行 | 只读仿真证据充分 | 多 Agent 执行后端与更高风险能力的独立决策 |
| 员工端侧 Agent | 保留为独立研究方向，评估 DeepSeek Harness 等候选的设备、隔离、凭据和审计边界 | 不接入真实交易、任意命令行（Shell）或跨目录写入 | 场景价值和数据边界明确，并批准合成数据 POC | 是否进入受限真实数据验证的独立决策 |

当前不并行建设第二套生产执行后端；出现资料无法回答的决策性不确定项时，可以开展隔离、限时、非生产的概念验证。后续仅在具体工作负载触发时比较替代方案，也不让某个热门框架覆盖所有场景。电力交易多 Agent 的具体边界见[附件 B](./unified-agent-platform-attachments/appendix-b-electricity-multi-agent)，DeepSeek Harness 的定位见[附件 A](./unified-agent-platform-attachments/appendix-a-deepseek-harness)。

## 平台演进规划

| 工作线 | 性质 | 当前安排 | 进入下一决策的条件 |
|--------|------|----------|--------------------|
| 最小统一控制面 | 近期建议 | 稳定现有链路，优先评估从 Agent BFF 演进 Gateway 后的统一 Agent API，并形成可信身份与资源绑定、最小 Run 账本、面向客户端的安全输出和审计约定 | 首个生产接入获准前，四类证据分别达到该场景的生产准入要求并留痕 |
| 执行后端选型 | 按需决策 | 核验 Dify 基线并保持可替换，不并行建设第二套生产执行后端；决策性不确定项可做隔离的非生产 POC | 拟进入生产、扩大使用规模、工作负载变化，或形成可复核缺口 |
| 场景扩展 | 条件式工作线 | 电力交易如启动，先做只读分析与确定性聚合；端侧 Agent 先做安全边界研究 | 各自场景价值、数据边界和风险控制明确 |
| 生产治理 | 持续工作线 | 从第一阶段开始持续补齐容量、容灾、灰度、升级、成本、评测和安全响应 | 随生产工作负载持续复审 |

该规划描述技术演进顺序，不预设具体执行后端、预算、组织角色或实施排期。

## 主要风险与管理关注点

| 风险 | 典型表现 | 管理关注点 |
|------|----------|------------|
| 身份、数据或执行边界失守 | 模型或客户端改变租户、资源、工具或执行范围 | 服务端绑定身份和资源；工具逐次授权；业务后端保留最终权限 |
| 平台范围扩张但价值不清 | 同时建设编辑器、执行后端、控制台、端侧和多 Agent | 从业务场景出发，优先统一不可替代的控制边界 |
| 当前实现或热门框架过早固化 | 将 Dify、Mastra、DeepSeek Harness 等直接定为公司标准 | 完整方案比较；保留可替换 API；按工作负载形成结论 |
| 技术试验代替生产证据 | Demo 成功即认为安全、可恢复、可运维 | 区分 Implemented、Deployed、Enforced 和 Verified |

本次汇报旨在统一 Agent 技术分类、公司现状、目标架构和选型方法。具体项目、候选验证和生产选型应在业务场景明确后分别评估。
