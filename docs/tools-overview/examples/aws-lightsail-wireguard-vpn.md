# 让 AI 在 AWS 上搭建 VPN

把下面的完整 Prompt 交给具备终端、AWS 和 SSH 操作能力的 AI，让它完成选型、部署、验证和客户端配置。你只需要提供使用需求、登录自己的 AWS 账号、确认费用，并在手机或电脑上验收。

## 使用前准备

- 一个可以创建 Lightsail 实例的 AWS 账号。登录和 MFA 在官方页面完成，不把密码、验证码或 Access Key 粘贴给 AI。
- 一台可以运行 AI 助手的电脑，以及在新节点建好前仍能访问 AI 和 AWS 的网络。
- 要使用的设备与客户端名称，例如 iPhone 上的 Shadowrocket、Windows 上的 Clash Verge Rev，或官方 WireGuard 客户端。

修改 Prompt 中的“我的需求”即可。不确定的项目可以保留默认值，让 AI 检查后给出方案。普通网页聊天若没有执行工具，只能协助规划；实际部署需要把任务交给有相应权限的 AI 助手。

## 完整搭建 Prompt

```text
请帮我在 AWS 上完成一套个人自用的 VPN/代理节点，负责从环境检查、资源创建、
服务部署一直到可导入的客户端配置和连接验证。请用中文与我沟通。

我的需求：
- 区域：东京（ap-northeast-1）。
- 节点数量：先建 1 个。
- 设备与客户端：iPhone / Shadowrocket；Windows / Clash Verge Rev。
- 已有 AWS 实例：无。如果我填写了实例名称与区域，请先检查是否适合复用。
- 月预算：尚未确定，请先查询当前套餐与流量费用并让我确认。
- 目标网站：github.com、www.cloudflare.com，以及我补充的网站。
- 协议：根据上述客户端与实际网络选择，先说明选择理由。
- 订阅：本次先完成单节点和独立配置，后续再配置固定订阅地址。
- 私有文件目录：请在本机选择专用目录，确保不在任何 Git 工作树中。

一、先核实环境和方案
检查本机系统、已有工具、AWS 登录身份、区域和权限。优先使用现有临时登录态、
IAM Identity Center 或 CloudShell；需要我登录时给出明确入口，不创建根用户 Access Key。
查询 AWS 当前可用的 Lightsail 套餐和 Ubuntu LTS 镜像，提出包含公网 IPv4、
满足服务内存需求并使用同区域静态 IPv4 的方案。
列出拟创建或复用的资源、月度基础费用、流量额度、超额收费和停止使用后的清理方式。
先让我确认这份具体方案和费用；确认后，直接完成范围内的部署与验证。
如果信息已能从环境中取得，请自行检查，不要让我重复提供。

二、完成服务部署
在方案和费用确认后，创建或复用实例，绑定静态 IPv4，再完成以下配置。
按客户端兼容性选择一种主方案。使用 Shadowrocket 和 Clash Verge Rev 时，
可采用 VLESS + REALITY / TCP 443；需要官方 WireGuard 客户端时，采用 WireGuard。
先核对当前官方文档、软件版本、服务器架构和端口占用，再安装受支持的版本。
采用轻量部署和系统服务管理，配置开机启动；默认不安装 Docker 或管理面板。
检查 Lightsail 与系统防火墙，分别核对 IPv4、IPv6 和 TCP、UDP 规则。
仅开放已选服务需要的入口，SSH 使用密钥并限制合理的来源；确认管理连接仍然可用。

如果选择 VLESS + REALITY：
生成真实的客户端身份和 REALITY 参数，实测 target、SNI、握手及客户端版本兼容性；
优先使用静态 IPv4 作为可验证的出口，生成与服务端参数一致的配置。
如果选择 WireGuard：
配置转发、NAT、DNS、路由和适合实际路径的 MTU，每台设备使用独立密钥与隧道 IP，
先检查网段冲突。可测试 UDP 443 或 51820，不假设某个端口一定可用。
TCP 443 与 UDP 443 分别检查；已有 HTTP/3、QUIC 或其他 UDP 服务时不要抢占 UDP 443。

三、交付客户端配置
根据我实际使用的客户端生成文件和导入说明。Shadowrocket 交付可扫码的节点二维码；
Clash Verge Rev 交付包含节点、策略组和 rules 的完整 YAML，并用兼容的 Mihomo 内核校验；
官方 WireGuard 客户端交付各设备独立的配置文件与二维码。
二维码必须反向解码，确认与对应配置一致。多设备需要可单独撤销的客户端身份。
沿用已有客户端规则；没有规则时先给出适合需求的方案，说明哪些请求会代理或直连。
明确 IPv6 和 DNS 的处理方式；若只接管 IPv4，说明边界，避免声称所有流量都经过节点。

四、用实际连接验收
检查服务状态、监听端口、错误日志、内存和磁盘余量。
从客户端侧显式连接这个新节点，完成协议握手，并验证出口 IP 与预期一致，
排除本机已有代理导致的测试混淆；不要用服务器直接访问网站代替客户端测试。
连续进行至少 10 次 HTTPS 请求，记录成功率、连接耗时和总耗时，并测试 DNS 与目标网站。
遇到失败时根据日志、路由和抓包证据定位，修复后重测，不仅凭超时就判断端口被封锁。
最后给我最少的手机/电脑操作步骤，让我在 Wi-Fi 与蜂窝网络分别验证。
无法代替我完成的真机测试应标明“待用户验收”，不能记为通过。

五、保留可维护的交付结果
已有实例、服务、Peer、密钥和业务端口先检查归属，修改前备份；
保留无关服务与客户端配置，避免重复创建资源或覆盖已有密钥。
替换资源、扩大费用或造成已有连接中断的操作，要先说明影响并取得我的确认。
凭据、二维码和完整配置只保存在私有目录：目录权限 0700，敏感文件 0600，
或当前操作系统上的等效访问控制；不要提交到 Git、公开分享或打印到日志。
保存本次使用的脚本和脱敏维护说明，记录资源、版本、文件位置、
新增设备、撤销设备、备份恢复及停止使用时释放资源的方法。

完成后简洁交付：资源与费用摘要、客户端文件和二维码位置、已验证的结果、
仍需我配合的步骤，以及日常如何检查节点。遇到必须由我完成的登录、费用确认、
权限授权或真机操作时，说明具体动作，其余已授权工作继续完成。
```

这个 Prompt 把容易遗漏的客户端配置、真实连接测试和后续维护一起交给 AI。具体命令由 AI 根据当时的环境生成并执行，脚本保存在本机，方便后续检查与重跑。

## 怎样判断已经搭好

重点看能否使用以及交付是否完整：

| 验收项 | 应该看到什么 |
| --- | --- |
| 资源与费用 | 实例所在区域、使用的套餐、静态 IP、流量额度和预计费用明确 |
| 客户端导入 | 二维码或配置成功导入，所选节点与新建实例对应 |
| 实际访问 | 请求确实经过该节点，出口符合预期，常用网站可连续访问 |
| 不同网络 | Wi-Fi 与蜂窝网络分别测试，失败的网络单独记录 |
| 后续维护 | 知道配置放在哪里、如何加设备、撤销访问和释放收费资源 |

“服务已启动”“端口可达”和“手机实际能上网”是不同的验证结果。规则模式下，只有命中代理规则的请求才会经过节点；验收时先确认测试请求选择了新节点。

## 后续怎么让 AI 继续维护

在原会话中描述目标和现象即可，例如：“新增一台手机，给它独立凭据”“检查这个节点，蜂窝网络连续几次请求失败”“增加新加坡备用节点，先给出新增费用”。保留 AI 交付的脱敏维护说明，新会话也能接着工作。

多个 VLESS REALITY 节点都可用后，可以继续使用 [让 AI 为 VPN 节点配置订阅](./aws-lambda-vless-reality-subscription) 中的完整 Prompt。这样客户端只导入一次订阅地址，后续通过刷新取得节点更新。

## 供 AI 核对的官方资料

实例创建与网络选项以 [AWS Lightsail 文档](https://docs.aws.amazon.com/lightsail/latest/userguide/getting-started-with-amazon-lightsail.html) 为准。服务端配置分别参考 [Xray REALITY 文档](https://xtls.github.io/config/transports/reality.html) 和 [WireGuard 入门文档](https://www.wireguard.com/quickstart/)。让执行任务的 AI 在部署时核对当前版本与费用。
